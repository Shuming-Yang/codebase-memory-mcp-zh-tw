15 個 MCP 工具

索引 / 查詢 / 讀取 / 維運 四類全解

總覽

類別工具
索引index_repository · list_projects · delete_project · index_status
查詢search_graph · trace_path · detect_changes · query_graph · get_graph_schema
讀取get_code_snippet · get_architecture · search_code
維運manage_adr · check_index_coverage · ingest_traces

索引類

index_repository索引把 repo 索引進圖；之後 auto-sync 保持新鮮。

核心參數 repo_path（絕對路徑）。首次全索引，之後增量。auto_index 開啟時（config set auto_index true）會在新專案連線時自動執行。結束時可選擇寫出 team-shared graph artifact（見 Graph Artifact）。

list_projects · delete_project · index_status索引列出 / 刪除 / 查狀態。

list_projects 回傳每個專案的 name（用於其他工具的 project 參數）、節點/邊數。 delete_project 移除專案與全部圖資料。index_status 查詢專案目前的索引狀態。

查詢類

search_graph查詢結構搜尋：name pattern、label、檔案過濾、degree 過濾、分頁。

最常用的發現工具。正則 name_pattern（如 .*Handler.*）、label（如 Function）、file_pattern、min_degree/max_degree、limit/offset 分頁。這是「先發現確切名稱」的入口——trace_path 與 get_code_snippet 都靠它找目標。

trace_path查詢BFS 遍歷——誰呼叫它、它呼叫誰。深度 1–5。

別名 trace_call_path。function_name + direction（inbound / outbound / both）。這是取代「grep 誰呼叫 X」的殺手級工具——在型別解析的圖上 BFS，<10ms。

query_graph查詢執行 Cypher-like 圖查詢（唯讀）。

openCypher 唯讀子集（Cypher 全解）。例如死碼偵測 MATCH (f:Function) WHERE NOT EXISTS { (f)<-[:CALLS]-() } RETURN f.name。子集之外的語法回傳明確的 unsupported … 錯誤，不會靜默回空。

detect_changes查詢把 git diff 映射到受影響符號 + blast radius + 風險分類。

讀取未 commit 的變更，映射到受影響的符號與風險等級。用於「改了這個會影響到誰」的影響分析。

get_graph_schema查詢節點/邊計數、關係 pattern、每個 label 的屬性定義。先跑這個。

探索圖結構的起點：看這個專案有哪些 label、邊型、屬性——決定接下來要問什麼。

讀取類

get_code_snippet讀取用 qualified name 讀函式原始碼。

用 <project>.<path_parts>.<name> 直接讀函式原始碼——不用先知道檔案路徑。qualified name 可用 search_graph 發現。

get_architecture讀取codebase 總覽：語言、套件、入口點、路由、熱點、邊界、分層、cluster。

一次呼叫拿整個專案的架構摘要。含社群 cluster（Louvain 偵測的功能模組）與 ADR 摘要。跨 repo 時也能給 cross-repo architecture summary。

search_code讀取grep-like 文字搜尋，只在已索引的檔案。

跟 grep 類似，但範圍限於圖索引的檔案——語意上有圖的加持（可顯示該 hit 對應到哪個符號）。

維運類

manage_adr維運Architecture Decision Record 的 CRUD。

把架構決策（ADR）持久化，跨 session 保留下來。query 模式（get/sections）用 server 的快取 query store，可以在同專案重索引進行中繼續服務；寫入仍序列化。

check_index_coverage維運針對一組路徑檢查索引涵蓋率。

檢查給定檔案路徑是否被索引、有無 flagged / skipped / excluded 範圍。agent 的 Verify / Auditor tier 用它做「證據路徑的涵蓋檢查」——clean 結果只代表「沒有記錄缺口」，不是完整證明。

ingest_traces維運收納 runtime traces 來驗證 HTTP_CALLS 邊。

把 runtime trace 資料收進圖，用真實執行資料驗證/補強 HTTP_CALLS 跨服務邊。

CLI 模式

每個 MCP 工具都能當單次本機指令跑（cli 子指令），不會啟動 daemon、不留常駐 process：

codebase-memory-mcp cli index_repository --repo-path /path/to/repo
codebase-memory-mcp cli list_projects
codebase-memory-mcp cli search_graph --project my-project --name-pattern '.*Handler.*' --label Function
codebase-memory-mcp cli trace_path --project my-project --function-name Search --direction both
codebase-memory-mcp cli query_graph --project my-project --query 'MATCH (f:Function) RETURN f.name LIMIT 5'

加 --json 拿完整 MCP result envelope；--progress 在非互動環境強制顯示進度（只寫 stderr，stdout 保持機器可讀）。

看完這頁你應該能說出：15 個工具的四類分法、search_graph 為何是發現入口、trace_path 如何取代 grep「誰呼叫誰」、以及每個工具都能用 cli 子指令在本機跑。

教學解說

CBM 的 15 個 MCP 工具分四類：索引（index_repository 等）、查詢（search_graph / trace_path / query_graph 等）、讀取（get_code_snippet / get_architecture 等）、維運（manage_adr / ingest_traces 等）。

最重要的入門模式是：先 search_graph 發現名稱 → 再 trace_path 追蹤關係 → 最後 get_code_snippet 讀原始碼。這三個工具的組合能回答大部分「這段程式碼在做什麼」的問題。

Worked Example

完整探索一個陌生 codebase 的工作流：

  1. 先看架構：get_architecture(project="my-project", aspects=["overview"]) — 拿到語言、套件、入口點摘要
  2. 搜尋目標：search_graph(project="my-project", name_pattern=".*auth.*", label="Function") — 找到所有 auth 相關函式
  3. 追蹤呼叫：trace_path(project="my-project", function_name="authenticate", direction="both") — 看誰呼叫它、它呼叫誰
  4. 讀原始碼：get_code_snippet(project="my-project", qualified_name="myproj.src.auth.authenticate") — 直接看實現
  5. 深入查詢：query_graph(project="my-project", query="MATCH (f:Function)-[:CALLS*1..3]->(t:Function) WHERE f.name = 'authenticate' RETURN t.name, count(*) AS freq ORDER BY freq DESC LIMIT 10")

常見錯誤 / 診斷

症狀原因解法
search_graph 找不到函式名稱不匹配或專案未索引用 list_projects 確認專案存在，用更寬鬆的 regex
get_code_snippet 回傳 qualified name 錯誤qualified name 格式不對先用 search_graph 拿到正確的 qualified_name
detect_changes 回傳空沒有未 commit 的變更先做 git modify 再試

進階實戰 · 改動前影響分析 + 上線後驗證的完整工具鏈

探索陌生 codebase 是「讀」；這裡示範「改」之前的維運流程，把 15 個工具當一條流水線用：

  1. 改之前：detect_changes(project="my-project")——讀取未 commit 的 diff，把變更映射到受影響符號並標風險等級。
  2. 確認證據涵蓋：check_index_coverage(project="my-project", paths=["src/core/order_service.go"])——確認你改的檔案真的進圖了，clean 只代表「沒有記錄缺口」。
  3. 沿風險往上查：trace_path(function_name="OrderService.UpdateStatus", direction="inbound", depth=3)——看誰直接或間接依賴它。
  4. 上線後驗證：用 ingest_traces 收 runtime trace，驗證真實的 HTTP_CALLS 邊——圖說「有呼叫」、跑起來「真的有呼叫」，兩者對齊才算完成驗證。
  5. 把決策留下來：manage_adr(mode="update", content="改用 event-driven 解耦 order 與 inventory")——跨 session 保留這次的架構決策。

為什麼選這條路徑：單一工具解決單一問題；但「改一個公共函式」需要「分析影響 → 確認涵蓋 → 追蹤風險 → 執行驗證 → 留下決策」五段閉環。這條路徑展示了索引工具如何不只是「查詢工具」，而是變更管理工具鏈。

深入原理 · 工具層的薄包裝設計與「以為 search_code 等於 grep」的誤解

mcp.c 是「門面」：15 個工具的 schema 以資料表註冊，收到 JSON-RPC 請求後解包、分派到 store/cypher、再包成結果回傳。真正的圖操作在 store/ 與 cypher/——所以 mcp.c 大部分是薄包裝。這個設計讓 CLI 模式可以直接複用同一批執行邏輯（cli search_graph --json 拿到完整 MCP result envelope）。

「大家以為正確其實有誤」的案例：search_code 看起來「就是 grep」，於是有人拿它搜整個硬碟，或期望它搜到「不在圖裡」的檔案。實際上 search_code 的範圍只限於已被索引的檔案（走 SQLite FTS5 + 自訂 camelCase tokenizer），而且結果會帶上語意資訊（該 hit 對應哪個符號）。同理，ingest_traces 被誤解為「會驗證所有邊」，但它的職責是收納 runtime trace 來補強/驗證 HTTP_CALLS——不是全域驗證器。先搞清楚每個工具的「範圍」再下結論。

進階疑難排解

症狀可能原因解決方案
工具回傳 project not foundproject 參數與 list_projects 的 name 不一致先跑 list_projects 拿正確 name（別自己猜）
detect_changes 一直回空沒有未 commit 的變更，或該目錄不是 git repo先確認 git 狀態；變更要先寫入再呼叫
check_index_coverage 標了 flagged該路徑被 ignore 或超出 auto_index_limit調整 .cbmignore / 設定，或對該路徑手動 index
manage_adr 在重索引時卡住寫入被序列化（query 走快取、寫入仍序列化）query 模式可繼續服務；寫入等重索引完成
CLI 模式輸出被 progress 污染未用 --json 且 --progress 強制開啟用 --json；progress 只寫 stderr、stdout 保持機器可讀

進階挑戰題

  1. 規劃一次「把一個公共函式從同步改非同步」的完整工具流程：每一步用哪個工具、期望看到什麼、如何驗證。
  2. 解釋「check_index_coverage clean 不等於完整證明」——它沒有記錄缺口，那缺的是什麼？（至少兩個面向）
  3. 為什麼把工具做成「薄包裝」能讓 CLI 與 MCP 共用同一套邏輯？這對測試與維護的影響是什麼？
