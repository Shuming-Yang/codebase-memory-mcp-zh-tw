Multi-Agent 支援

43 個平台、Scout/Verify/Auditor 三層、conditional/explicit

Conditional 的意義

「Conditional」指 installer 只在已存在的 config 路徑或文件化平台證明目標 active 時才寫入。它絕不：翻開實驗性 feature flag、啟用 plugin、YOLO modes、global permission bypass、或第三方指令信任。

Scout / Verify / Auditor 三層

有文件化 custom-agent format 的平台，installer 從一份 canonical contract 產生三層定義：

Tier定位行為
Scout（Tier 1）快速試探發現約 3–4 個窄呼叫；不做 absence / exhaustive-impact / dead-code 聲稱
Verify（Tier 2，預設）任務導向證據任務導向圖證據 + 精確原始碼檢查 + 引用路徑涵蓋 + 範圍涵蓋
Auditor（Tier 3）完整稽核受限範圍 + 目前索引 generation + 完整分頁 + 更廣關係檢查 + 明確未解限制

每層都批次呼叫 check_index_coverage 檢查證據路徑；clean 只代表「沒有記錄缺口」，不是完整證明。更新的 migration 只覆寫 byte-identical 的先前 Verify 定義，不覆蓋使用者改過的 agents。

工具 profile（Kiro / Junie / Qoder / Factory）

某些平台用正向 allowlist 的 server profile 限制工具面：

  • Kiro：Scout 用 --tool-profile scout（7 個工具）、Verify/Auditor 用 analysis（11 個）。
  • Junie：註冊同名 server alias（schema 依 server 過濾）。
  • Qoder：named-server 選擇 + 精確 tier-specific MCP tool IDs。
  • Factory：精確 registered IDs，不用 additive mcpServers field。

hooks：fail-open、context-only

安裝的 hooks 都是 fail-open 且 context-only：Claude 的 PreToolUse 觀察 Grep/Glob 並把匹配的圖符號注入 additionalContext；PostToolUse 的 Read 在圖無法完整解析該檔時加涵蓋 context。它永遠不拒絕或替換工具呼叫。

教學解說

CBM 支援 43 個 agent 平台，這是透過 install 指令自動設定各平台的 config 實現的。核心概念是 Scout / Verify / Auditor 三層：Scout 做快速試探（3-4 個窄呼叫）；Verify 做任務導向的證據收集；Auditor 做完整稽核。

三層的設計哲學是漸進式深入——不要一開始就做完整掃描，而是先快速找到方向，再針對性地深入。這節省 token 也節省時間。

Worked Example

使用 Scout 層快速探索陌生 codebase：

# Scout 層：快速發現（約 3-4 個窄呼叫）
search_graph(project="mystery-project", name_pattern=".*main.*", label="Function")
get_architecture(project="mystery-project", aspects=["overview"])

# Verify 層：任務導向深入
trace_path(project="mystery-project", function_name="handleRequest", direction="inbound")
get_code_snippet(project="mystery-project", qualified_name="mystery.src.server.handleRequest")

# Auditor 層：完整稽核
query_graph(project="mystery-project", query="MATCH (f:Function) WHERE NOT EXISTS { (f)<-[:CALLS]-() } RETURN f.name LIMIT 50")
check_index_coverage(project="mystery-project", paths=["src/handler.ts"])

進階實戰 · 團隊統一部署 CBM 到 43 個平台

個人安裝很簡單；10 人團隊、每人用不同 agent（有人 Claude Code、有人 Codex、有人 Cursor）時，需要一套統一 rollout 流程：

  1. 盤點平台：先確認每個成員「真的在用」哪些 agent——conditional 安裝只會寫入「已存在 config 路徑」的平台，所以盤點決定誰的機器會裝到什麼。
  2. 跑 install：codebase-memory-mcp install——37 個自動偵測 + 6 個 conditional/explicit 全寫入。檢查每個平台被寫了哪些東西（MCP config、AGENTS.md/skill、hooks）。
  3. 驗證三層 agent：有 custom-agent 格式的平台會從 canonical contract 產生 Scout / Verify / Auditor 三層定義——確認三層都存在且可被呼叫。
  4. 版本管理：建立「所有成員同一 CBM 版本」的規範——否則 admission barrier 會開始記錄 daemon-conflicts。
  5. 更新機制：團隊升級走「先備好再換」流程，統一重啟 session。

為什麼選這條路徑：Multi-agent 支援的價值不在「支援 43 個」，而在「同一個 CBM 圖、同一個三層協定，出現在每個人的 agent 裡」——團隊的 AI 協作有共同的工具語言。從個人到團隊，重點從「裝得起來」變成「版本一致 + 三層齊全 + 更新同步」。

深入原理 · Installer 的寫入模型與「以為 install 會全平台亂寫」的誤解

installer 的寫入是資料導向的：每個平台 = 一段 config 寫入描述 + 對應的 context 檔（AGENTS.md / GEMINI.md 等）+ skill + hooks。它從一份 canonical contract 生成三層 agent 的定義。更新的 migration 只覆寫byte-identical 的先前 Verify 定義——也就是「跟我們上次寫的一模一樣的版本」才會被覆寫；使用者改過的 agents 不會被悄悄蓋掉。

「大家以為正確其實有誤」的案例：看到「43 個平台」四個字，很多人以為 installer 會「把設定寫進每一種 agent 的設定檔」。實際上 conditional 平台只在「已存在的 config 路徑或文件化證明該平台 active」時才寫入——沒安裝的 agent 不會被碰。而 hooks 的設計是 fail-open + context-only：它只觀察 Grep/Glob/Read 並把圖符號注入 context，永遠不拒絕或替換工具呼叫。誤解成「hooks 會攔截我的操作」的人，會錯誤地關掉 CBM 提供的 hooks。

進階挑戰題

  1. 解釋為什麼 hooks 必須設計成「fail-open + context-only」而不是「攔截並替換工具呼叫」——風險是什麼？
  2. 設計一份「團隊 CBM 部署 SOP」，涵蓋平台盤點、版本統一、三層驗收、升級流程。
  3. 「conditional 安裝」和「亂寫所有平台」的差別，在安全上為何重要？舉一個具體的風險情境。

專案級端到端 Worked Example — 10 人異質 agent 團隊的統一部署

假設你的 10 人團隊中，有人用 Claude Code、有人用 Codex、有人用 Cursor、有人用 VS Code。你要確保每個人都能用到 CBM 的三層 agent。

  1. 平台盤點：確認每個成員「真的在用」哪些 agent——conditional 安裝只寫入「已存在 config 路徑」的平台。
  2. 統一版本：鎖定 CBM 版本，所有成員用同一版本。
  3. 跑 install：codebase-memory-mcp install——37 個自動偵測 + 6 個 conditional/explicit 全寫入。
  4. 驗證三層 agent：在每個平台上呼叫 Scout（search_graph）+ Verify（trace_path）+ Auditor（query_graph）確認三層都存在。
  5. 驗證 hooks：在 Claude Code 上跑 Grep，確認 PreToolUse hook 把圖符號注入 additionalContext。
  6. 建立更新機制：團隊升級走「先備好再換」流程。
