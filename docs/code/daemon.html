daemon/ — 會話協調

一帳號一 daemon、IPC、admission barrier
目錄：src/daemon/（daemon.c 847 行 + application.c + ipc.c + runtime.c…）

大方向

daemon/ 是「每帳號一個協調者」的實作。它管：daemon 的啟動/bootstrap（bootstrap.c）、前台 session 的 IPC（ipc.c）、應用程式 job 排程（application.c）、與 runtime 生命週期（runtime.c）。

1. Daemon 啟動

bootstrap.c · daemon.c daemon/daemon 的啟動、鎖、與生命周期。

第一個 daemon-backed session 啟動 daemon（bootstrap）；最後一個 session 關閉它。daemon 持有共享的 watcher/索引 jobs/UI。

2. IPC

ipc.c（cbm_daemon_ipc_*） daemon/前台 session ↔ daemon 的通訊。

IPCS 層封裝 session 與 daemon 之間的通訊：endpoint 位址、frame 收送、lifetime reservation、startup gate。平台差異（POSIX socket vs Windows）在 ipc_* 相關檔案中抽象。

3. Application 排程

application.c（cbm_daemon_application_*） daemon/索引 job 的排程、執行、取消。

daemon 收到「幫我索引 X」就排一個 application job。job 有物理上限、busy queue、可被 activation 取消。測試透過 _for_test() 鉤子注入失敗/延遲。

4. Runtime & admission

runtime.c · project_lock.c daemon/runtime worker 與 per-project 鎖。

runtime 管理 daemon 的 worker/process 生命週期；project_lock 提供 per-project 的 OS-backed 鎖，序列化同專案的並行寫入（CLI 與 MCP session 共用）。

看完這頁你應該能說出：daemon 的 bootstrap/lifecycle、IPC 封裝了平台差異、索引是 daemon 的 application job、以及 per-project lock 讓 CLI/MCP 並行寫入不會衝突。

教學解說

daemon 模組處理 session 協調、IPC、admission barrier、lifecycle。這是 CBM 多 session 共享資源的基礎設施。

進階實戰 · 追蹤一個索引 job 的排程、執行與取消

「我下 index_repository，圖就建好了」——中間其實是一個 application job 的生命週期：

  1. 請求進來：MCP session 對 daemon 發「幫我索引 X」（cbm_daemon_ipc_* 走 IPC frame）。
  2. 排程：application.c 的 cbm_daemon_application_* 把它排成 job——有物理上限與 busy queue；search_graph(project="cbm", name_pattern=".*application_job.*", label="Function") 找到它。
  3. 執行：job 跑到 runtime（runtime.c 管 worker/process 生命週期），對 pipeline 發起索引，per-project lock（project_lock.c）保證同專案不會並行寫入。
  4. 取消：如果 update 流程要替換二進位，會觸發 activation——daemon 取消執行中的 job（cbm_pipeline_cancel），等安全停止後才換 binary。

為什麼選這條路徑：這個流程橫跨 ipc → application → runtime → pipeline 四個元件。追蹤它，你才理解「索引」不是 mcp 直接做的事，而是 daemon 管理的共享資源——這正是「一帳號一 daemon」架構的實際價值所在。

深入原理 · IPC 抽象與「以為 daemon 是單執行緒」的誤解

daemon 的 IPC 層（ipc.c）封裝了三件事：endpoint 位址（session 與 daemon 怎麼找到彼此）、frame 收送（訊息的包裝）、lifetime reservation / startup gate（session 註冊與同步啟動）。平台差異（POSIX socket vs Windows named pipe 等）被抽在 ipc_* 相關檔案裡。測試透過 _for_test() 鉤子注入失敗/延遲，驗證「job 卡住時系統會怎樣」。

「大家以為正確其實有誤」的案例：看「daemon」兩個字，有人以為它是「一個負責所有事情的單一執行緒」，於是推斷「多 session 同時索引會互相卡死」。實際上 daemon 內部有 runtime worker 與 job 排程，索引請求是排程的 job（有 busy queue），不是直接串行執行；而 per-project lock 只序列化「同一專案」的寫入，不同專案可以平行。把「單一 daemon process」誤解成「單一執行緒」，會對並行能力做出錯誤預測。

進階疑難排解

症狀可能原因解決方案
索引請求排不到application job 物理上限滿或 busy queue 積壓等前面的 job 完成；或用 CLI 直接索引（走 per-project lock 佇列）
取消沒生效取消是非同步的，job 需要到可取消點才停止稍候再查 job 狀態；確認沒有殘留寫入
同專案兩個 session 都卡在等待per-project lock 互等（設計預期）確認是否真的需要並行；等待是正常行為，不會死鎖
IPC 連不上 daemonendpoint 失效或 daemon 已死看 cbm-daemon.log；必要時清理失效的 endpoint/lock
測試環境下 job 行為不穩定測試注入的失敗/延遲鉤子在作用檢查是否有 _for_test 設定殘留；clean build 再跑

進階挑戰題

  1. 解釋 per-project lock 如何「序列化同專案寫入」而「允許跨專案平行」——這對多 session 協作的並行能力有何意義？
  2. 設計一個崩潰復原測試：daemon 在索引中途被 kill，如何驗證「圖不會留下半寫狀態」？
  3. 「lifetime reservation」與「startup gate」各解決什麼問題？如果缺了它們會發生什麼？
