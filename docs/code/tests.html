tests/ — 測試策略

6,768 tests / 120 suites：Hybrid LSP 覆蓋是重頭戲
目錄：tests/（6,768 tests / 120 suites）

大方向

CBM 的測試量非常大（6,768 tests / 120 suites）。特別值得注意的是 Hybrid LSP 各語系的覆蓋測試——每個支援的語言都有一大堆「這個模式要解析到那個目標」的斷言測試。

1. 測試分類

test_<lang>_lsp.c tests/Hybrid LSP 各語系解析測試（最大的測試群）。

graphify 案例中最大的社群就是這些：test_c_lsp.c（602 節點社群）、test_rust_lsp.c、test_php_lsp.c、test_java_lsp.c、test_ts_lsp.c、test_kotlin_lsp.c、test_py_lsp.c。每個都斷言「某段程式碼的某個呼叫解析到正確目標」。這是「Go to Definition 等級解析」品質的來源。

test_cypher.c · test_store.c · test_cli.c · test_daemon*.c tests/核心模組的單元測試。

Cypher 引擎、store、CLI、daemon 各有專屬測試檔。多數函式有 _for_test() 鉤子讓測試注入失敗/延遲（可測試性設計）。

2. 特殊測試

test-infrastructure/ · repro/ · scale_contract.sh tests/回歸、重現、規模契約。

repro/ 放 issue 重現（repro_issue408…）；scale_contract.sh 驗證規模行為（大 repo 不退化）；smoke_guard.sh 做煙霧守衛。還有 grammar_cases.h 涵蓋各文法邊界案例。

3. 如何跑

scripts/test.sh scripts/測試入口（與 CI gate 相同）。 
scripts/test.sh                     # full: clean sanitizer build + all suites + guards
scripts/test.sh --suites <name>     # 單一 suite，增量，幾秒
build/c/test-runner --list-suites   # 看有哪些 suite

CI gate 也跑 scripts/test.sh——本機過 = CI 過。另有 test_build_dir_safety.sh、test_cpp_index_hang.sh 這類 shell 守衛。

看完這頁你應該能說出：CBM 的測試主力是 Hybrid LSP 各語系的解析斷言、_for_test() 鉤子讓核心可測、repro/ 放 issue 重現、以及 test.sh 與 CI gate 相同。

教學解說

CBM 有 6,768 個測試，覆蓋所有模組。測試策略包括單元測試、整合測試、Hybrid LSP 各語系測試。

進階實戰 · 為 Hybrid LSP 加一個語法案例（TDD 流程）

假設你發現 TypeScript 的某個 pattern（例如 optional chaining + generics）解析錯，修復它的標準流程：

  1. 先寫會失敗的測試：在 test_ts_lsp.c 加一個斷言——「這段 TS 的 user?.profile?.getName() 必須解析到 Profile.getName」。
  2. 只跑這個 suite 驗證紅燈：scripts/test.sh --suites ts_lsp——確認新案例真的失敗（這證明測試有效，也重現了 bug）。
  3. 修 pass：在 pass_lsp_cross.c / internal/cbm/lsp/ 的 TS 型別解析加上 optional chaining 的 unwrap 處理。
  4. 驗證綠燈：重跑 suite 直到通過，再跑 scripts/test.sh 全量（CI gate 相同——本機過 = CI 過）確認沒有 regress 別的語言。

為什麼選這條路徑：CBM 的測試主力正是 Hybrid LSP 的語系斷言——6,768 個測試裡最大的一群（test_ts_lsp.c、test_py_lsp.c、test_rust_lsp.c…）。用「先寫斷言」的方式參與，既重現 bug 又永久防回歸，這是這個專案對待解析品質的標準方式。

深入原理 · 6,768 測試的結構與「以為測試過就保證解析正確」的誤解

測試分三層：語系 LSP 斷言（每個支援語言一大疊「這段 code 的這個呼叫要解析到那個目標」）、核心模組單元測試（cypher/store/cli/daemon，多數函式有 _for_test() 鉤子注入失敗/延遲）、特殊測試（repro/ 放 issue 重現、scale_contract.sh 驗證大 repo 不退化、smoke_guard.sh 煙霧守衛、grammar_cases.h 文法邊界案例）。scripts/test.sh 與 CI gate 完全一致——本機過 = CI 過。

「大家以為正確其實有誤」的案例：6,768 個測試全綠，很容易被讀成「所有解析都正確」。但每個測試斷言的是「這個具體片段」——測試再多是「有限案例集」，而程式語言是「無限組合」。所以「測試過」只代表「涵蓋過的案例沒壞」；沒被 grammar_cases 或語系斷言涵蓋的模式（新 framework 的語法糖、極端泛型巢狀）仍可能解析錯。正確心態：測試是「防回歸的安全網」，不是「解析正確性證明」——遇到新 pattern，先加斷言再信任。

進階疑難排解

症狀可能原因解決方案
全量測試要跑很久6,768 測試 + sanitizer build 全跑很慢開發期用 --suites <name> 增量跑；上 CI 才跑全量
某 suite 名字記錯suite 命名與檔案名不完全對應build/c/test-runner --list-suites 列出正確名字
測試在本機過、CI 掛環境差異（compiler/sanitizer 旗標）確認本機用 scripts/test.sh 跑（含 sanitizer），不要用自訂指令
新增案例後別的語言 regress跨語言的共用邏輯被動到重跑全量；用 git diff 檢查 lsp/ 共用程式碼
repro 案例跑不出 issue 的 bugrepro 依賴特定版本/環境確認 repro 對應的 commit/版本；必要時更新 fixture
