discover/ + watcher/ — 檔案發現與自動同步

哪些檔案進圖、變更了怎麼重索引
目錄：src/discover/ · src/watcher/

大方向

discover/ 決定「哪些檔案進圖」，watcher/ 決定「檔案變了之後怎麼保持圖新鮮」。兩者都跟 忽略規則 密切相關。

1. discover/ — 檔案發現

cbm_discover() discover/discover.c走訪目錄，回傳要索引的檔案清單。

走訪 repo，套用忽略規則：

  1. 硬編碼模式（.git、node_modules…）
  2. .gitignore 階層
  3. .cbmignore（專案專用，gitignore 語法）
  4. symlink 永遠跳過
cbm_matches_fast_pattern() · cbm_should_skip_dir() · cbm_should_skip_filename() discover/discover.c快速過濾：路徑/目錄/檔名的跳過判斷。

為了在 75K 檔的 repo 上也能快速走完，discover 用 fast pattern 匹配（非逐檔 regex）過濾，並對目錄層級提前剪枝。

language.c · gitignore.c discover/語言偵測與 gitignore 解析。

language.c 依副檔名判斷語言（配合 extra_extensions 的映射）；gitignore.c 解析 .gitignore 語法（含 ! 反轉）。

2. watcher/ — 自動同步

cbm_watcher_new() · cbm_watcher_poll_once() · cbm_watcher_run() watcher/watcher.c背景監看、git polling、adaptive intervals。

watcher 由 daemon 擁有（跨 session 共享）。它輪詢 git 狀態偵測變更，用 adaptive interval 平衡「即時」與「省資源」。偵測到變更就觸發增量重索引（寫 Fast tier 的 graph.db.zst）。auto_watch false 可關掉。

看完這頁你應該能說出：檔案進圖的三層忽略 + symlink 規則、fast pattern 如何支撐 75K 檔走訪、watcher 由 daemon 共享且用 adaptive interval、以及 auto_watch 的開關。

教學解說

discover 模組負責檔案發現：.gitignore → .cbmignore → symlink 處理。這是索引管線的第一步。

Worked Example

追蹤檔案發現流程：

# 1. 找到 discover 入口
search_graph(project="cbm", name_pattern=".*discover_files.*", label="Function")

# 2. 找到 gitignore 解析
search_graph(project="cbm", name_pattern=".*gitignore.*", label="Function")

# 3. 找到 cbmignore 解析
search_graph(project="cbm", name_pattern=".*cbmignore.*", label="Function")

進階實戰 · 除錯「為什麼這個檔案沒進圖」

最常見的索引問題不是「慢」，而是「檔案不見了」。以「我明明有 legacy/helper.js，但圖裡沒有它」為例：

  1. 確認檔案真的被走訪：check_index_coverage(project="my-project", paths=["legacy/helper.js"])——它會回傳 indexed / skipped / excluded / flagged 四種狀態之一。
  2. 檢查 ignore 層：三層依序是硬編碼模式（.git、node_modules）→ .gitignore 階層 → .cbmignore。用 git check-ignore legacy/helper.js 看 git 層；再看 .cbmignore 有沒有比對到它。
  3. 檢查 symlink：如果 legacy/ 是 symlink，檔案永遠不會進圖——symlink 一律跳過（防循環、防越界）。
  4. 檢查語言偵測：language.c 依副檔名判斷；helper.js 沒問題，但如果是 helper.custom 這種自訂副檔名，就要靠 extra_extensions 映射。
  5. 檢查 watcher：如果是「新增」的檔案，watcher 可能還沒偵測到——cbm_watcher_poll_once() 手動觸發一次，或直接重跑 index_repository。

為什麼選這條路徑：檔案沒進圖的原因至少有五種（ignore、symlink、語言、範圍、時間）。先跑 check_index_coverage 得到官方判定，再逐層往下查，比亂猜「是不是 bug」有效——大部分時候是規則設定問題。

深入原理 · Fast pattern 與「以為 symlink 會跟著走」的誤解

75K 檔的 repo 不能逐檔跑 regex 判斷跳不跳過——cbm_matches_fast_pattern() 用快速 pattern 匹配，並在目錄層級提前剪枝（cbm_should_skip_dir()）：一個目錄被排除，整個子樹都不走。gitignore 解析（gitignore.c）支援 ! 反轉與階層式規則。watcher 由 daemon 擁有，用 git polling + adaptive interval 平衡即時與資源。

「大家以為正確其實有誤」的案例：很多人假設「symlink 指向的內容會被當成普通檔案索引」——例如 node_modules 或 vendor 用 symlink 指向別處。實際規則永遠跳過 symlink，即使它指向 repo 內的檔案：目的是防循環（symlink 可以指回自己造成無限走訪）與防越界（指到 repo 外洩漏不該進圖的檔案）。所以「我有個 symlink 的 src，怎麼圖是空的」——答案不是 bug，是規則。

進階疑難排解

症狀可能原因解決方案
檔案在但圖裡沒有被 ignore 或 symlink 排除，或 watcher 未偵測先跑 check_index_coverage 拿官方判定，再逐層排查
新增檔案要等很久才出現adaptive interval 較長（為省資源）等下一次 poll；或重跑 index_repository 立即更新
語言偵測錯誤自訂副檔名沒映射用 extra_extensions 設定副檔名 → 語言映射
!important.js 的反轉規則沒生效gitignore 的 ! 無法復活「被父目錄排除」的檔案改在父層目錄放行，或用 .cbmignore 另列白名單
一個被排除的目錄拖慢全索引目錄級剪枝沒生效（規則寫在太深層）把排除規則寫在父目錄層級，讓剪枝早點發生

進階挑戰題

  1. 寫一組 .cbmignore 規則：排除 build/、*.min.js、以及 generated/ 底下的 proto 檔，同時保留一個例外。
  2. 解釋「目錄級剪枝」為何能讓 75K 檔的 repo 走完——從時間複雜度角度說明它和逐檔 regex 的差別。
  3. 設計一個測試：驗證「symlink 指向 repo 內的檔案不會被索引」這條規則（參照 test_discover 風格）。
