pipeline/ — 多 pass 索引

索引管線的調度與 pass 註冊
檔案：src/pipeline/pipeline.c（2,524 行）· registry.c（1,031 行）· pipeline.h

大方向

pipeline.c 是把「一堆 source 檔」變成「一堆節點/邊」的總指揮。它管：pass 的註冊與執行順序、平行調度（pass_parallel.c 的 worker pool）、專案識別、以及最後把結果 publish 給 store。

1. Pipeline 生命週期

cbm_pipeline_new() · cbm_pipeline_run() · cbm_pipeline_free() pipeline.cpipeline 的建立、執行、釋放。

new 初始化專案狀態（project name、cache、store 關聯）；run 依序跑所有註冊的 pass；free 清理。set_before_publish_hook_for_tests 這類 for_test hook 是 CBM 的可測試性設計——很多函式有測試鉤子。

cbm_pipeline_cancel() pipeline.c讓執行中的索引可被取消（daemon activation 時用）。

更新流程要求所有 process 取消時，執行中的索引透過此函式安全停止——不會留下半寫的圖。

2. Pass 註冊（registry.c）

pass 註冊表 registry.c每個 pass 一個登錄項：名稱、前置條件、執行函式。

registry.c 是 pass 的清單。pipeline 依 registry 的順序執行每個 pass，每個 pass 把節點/邊 publish 到 store。想看各 pass 細節見 passes.html。

3. 平行化

pass_parallel / worker_pool pipeline/把可並行的抽取分散到多個 worker。

大 repo 的索引速度靠平行 worker 撐起來（Linux kernel 3 分鐘的秘密之一）。CBM_WORKERS 可覆寫偵測到的 worker 數。

看完這頁你應該能說出：pipeline 的 new/run/free 生命週期、pass 靠 registry 註冊與依序執行、可取消性如何支援更新流程、以及平行化如何貢獻索引速度。

教學解說

pipeline 模組負責多 pass 索引的調度。pipeline.c 是主控，registry.c 管理各 pass 的註冊與執行順序。

Worked Example

追蹤索引管線的執行：

# 1. 找到 pipeline 入口
search_graph(project="cbm", name_pattern=".*pipeline_run.*", label="Function")

# 2. 找到 pass 註冊
search_graph(project="cbm", name_pattern=".*register_pass.*", label="Function")

# 3. 看各 pass 的執行順序
trace_path(project="cbm", function_name="pipeline_run", direction="outbound")

進階實戰 · 追蹤一次增量重索引

全索引只發生一次；日常運作靠增量。以「我改了一個檔案，圖什麼時候、怎麼更新」為例：

  1. 偵測：watcher（由 daemon 擁有）用 git polling 偵測到變更，觸發增量重索引。
  2. 範圍：cbm_pipeline_run() 跑的是「針對變更檔案的抽取 + 合併」，不是重跑全部 pass——search_graph(project="cbm", name_pattern=".*incremental.*", label="Function") 找增量邏輯。
  3. 更新：變更檔的節點/邊被重新計算、更新到 store；受影響的跨檔邊（如它被誰呼叫）也一併修正。
  4. 落盤：watcher 的增量用 Fast tier 寫 graph.db.zst（zstd -3）——低延遲、不阻塞。
  5. 查詢一致性：之後任何查詢都看到新 generation 的圖——所以「改 code 後查詢結果沒變」，通常是 watcher 沒跑（auto_watch false）而不是 pipeline 的問題。

為什麼選這條路徑：增量是「索引不必每次全跑」的關鍵，也是效能頁「3 分鐘 kernel」之外的另一半故事。追蹤它，你才能診斷「改了 code 但圖沒更新」這類日常問題。

深入原理 · RAM-first + 單次 dump + 可取消性

pipeline 的生命週期是 cbm_pipeline_new → run → free：new 初始化專案狀態（project name、cache、store 關聯）；run 依 registry 依序跑 pass；free 清理。索引全程在記憶體（LZ4 HC 壓縮讀入 + in-memory SQLite），結束才單次 dump 到磁碟，之後記憶體釋放回 OS。可取消性由 cbm_pipeline_cancel() 提供——更新流程要求「所有 process 取消」時，執行中的索引安全停止，不會留下半寫的圖。測試透過 set_before_publish_hook_for_tests 這類鉤子注入可觀察點。

「大家以為正確其實有誤」的案例：RAM-first 的「單次 dump」讓很多人以為「索引完成前，之前的圖完全不可用」——但 daemon 的共享 job 系統 + store 的 WAL 模式讓舊圖在重索引期間仍可查詢（讀的是舊 generation，索引完成切換到新 generation）。把「重索引」想像成「整段停機」，會對「索引期間查詢為何可用」產生錯誤預期。

進階疑難排解

症狀可能原因解決方案
改了 code 圖沒更新watcher 未啟用或 git 狀態沒變config set auto_watch true；確認變更有 commit/stage 或 tracked
增量後某些舊邊還在被刪除的符號的邊未被清理跑一次完整 index_repository 做校準
索引期間查詢很慢重索引與查詢競爭資源（讀舊 generation）接受暫時慢；或排程在低峰時段跑全索引
取消索引後圖還是完整的可取消性只在 publish 點生效，未完成的 pass 不落盤這是設計預期；不用擔心半寫狀態
測試 hook 影響了正式行為_for_test 設定殘留在正式環境clean build；確認測試鉤子只在測試二進位啟用

進階挑戰題

  1. 解釋「RAM-first + 單次 dump」如何支撐「3 分鐘索引 kernel」——對比「逐檔案落盤」的差異。
  2. 設計一個「可取消索引」的測試：啟動索引→觸發取消→驗證圖仍是上一個完整 generation。
  3. 如果一個 pass 失敗，pipeline 該 abort 還是繼續？列出兩種策略的利弊，並說明 CBM 為何選擇容錯。
