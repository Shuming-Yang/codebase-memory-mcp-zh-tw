semantic/ — 語意搜尋

nomic-embed-code、11-signal 計分、MinHash/ROTSQ
目錄：src/semantic/（semantic.c + rotsq.c + ast_profile.c + minhash.c）

大方向

semantic/ 讓 semantic_query 可以用自然語言找程式碼——不需要 API key、Ollama、Docker，因為向量模型（nomic-embed-code，768d int8）編譯進二進位。

1. 向量搜尋

semantic.c semantic/semantic_query 的核心：embedding 比對 + 組合計分。

查詢文字被轉成 embedding，與圖中節點比對。但它不是「單一向量距離」——而是 11-signal 組合計分：TF-IDF、RRI、API/Type/Decorator signatures、AST profiles、data flow、Halstead-lite、MinHash、module proximity、graph diffusion 等加權合成。

2. ROTSQ 與 AST profile

rotsq.c · ast_profile.c semantic/ROTSQ 與 AST 特徵輪廓。

單靠 token 向量會漏掉「結構上像」的函式。ast_profile 把 AST 的形狀（巢狀、呼叫數量、參數模式）編成特徵，rotsq 提供另一種訊號——讓「詞彙完全不同但做的事一樣」的函式也能被找到。

3. MinHash（近複製）

minhash.c semantic/ + simhash/SIMILAR_TO 邊的底層：Jaccard 近複製偵測。

MinHash + LSH 對大圖做近似重複偵測，產出 SIMILAR_TO 邊（Jaccard 計分）——找 copy-paste 程式碼。

看完這頁你應該能說出：semantic 搜尋為何不需要 API key（模型編譯進二進位）、11-signal 計分比單一向量距離強在哪、AST profile/ROTSQ 怎麼補 token 向量的盲點、以及 MinHash 產出 SIMILAR_TO。

教學解說

semantic 模組處理語意搜尋：nomic-embed-code embeddings（768d int8）、11-signal scoring、MinHash/ROTSQ。這是 CBM v0.9 新增的核心能力。

進階實戰 · 除錯「語意搜尋回傳不直覺的結果」

你問「找出所有負責重試的函式」，結果第一頁全是無關的 retry_count 變數。這條路徑幫你把語意搜尋變可靠：

  1. 確認 embedding 模型有載入：nomic-embed-code（768d int8）編譯進二進位——確認你的 build 不是跳過 semantic 的 lean 版（search_code(project="cbm", pattern="nomic") 找載入處）。
  2. 理解計分不是單一距離：結果是 11-signal 組合（TF-IDF、RRI、API/Type/Decorator signatures、AST profile、data flow、Halstead-lite、MinHash、module proximity、graph diffusion 等加權）——search_graph(project="cbm", name_pattern=".*signal.*", label="Function") 找計分函式。
  3. 換關鍵字策略：純 token 相似度會被「同名不同義」帶偏；試著在查詢裡混入「結構特徵詞」（例如「帶 sleep 的重試」）讓 AST profile / data flow 訊號介入。
  4. 用 cross-check 收斂：把語意結果與 search_graph / search_code 的結果對照——三個工具的「相關」定義不同，交集往往是真正目標。

為什麼選這條路徑：語意搜尋「不直覺」多半不是壞了，而是你誤以為它是「關鍵字搜尋的智慧版」。理解 11-signal 架構後，你能透過「餵結構特徵詞」和「多工具交集」把召回率從「碰運氣」變成「可控制」。

深入原理 · 11-signal 計分與「以為語意搜尋 = 純向量距離」的誤解

很多人看到「embedding 模型」就以為 semantic_query 是「查詢 embedding 與節點 embedding 比餘弦距離，取 top-k」。實際架構是多訊號加權合成：詞彙訊號（TF-IDF）、結構訊號（AST profile 把巢狀/呼叫數/參數模式編成特徵）、語意訊號（embedding 相似度）、關係訊號（graph diffusion、module proximity）等共 11 種，各自加權後合出分數。ROTSQ 提供另一種「詞彙完全不同但做的事一樣」的訊號。這正是「語意搜尋能跨詞彙」而「關鍵字搜尋不行」的關鍵——semantic_query 工具用的就是這套。

「大家以為正確其實有誤」的案例：正因為有 embedding，很多人斷言「語意搜尋需要 API key / 會外傳 code」——但模型是編譯進二進位的（nomic-embed-code，768d int8），100% 本機推理、零外傳。另一個誤解是「分數越高代表越相關」——11-signal 是加權合成，不同專案的最佳權重可能不同，所以「高分」可能被「詞彙訊號」單獨拉高，而「結構訊號」完全缺席。把「高分」當「絕對相關」是常見誤用。

進階挑戰題

  1. 解釋 11-signal 架構如何讓語意搜尋「跨詞彙」——相較於單一 embedding 距離，它多捕捉了哪些面向？
  2. 設計一個實驗：同一查詢在「含結構詞」與「不含結構詞」兩種寫法下比較結果，判斷結構訊號對召回率的影響。
  3. 「embedding 模型編譯進二進位」帶來哪三項具體好處（安全/部署/成本）？列出並說明。
