cli/cli.c — 安裝與設定層

install/uninstall/update/config、43 個 client surface、hook 安裝
檔案：src/cli/cli.c（11,928 行）· cli.h

大方向

cli.c 是「安裝體驗」的所在。它做的事包括：install（下載/驗證/啟動）、uninstall、update（印出重跑 install.sh 的指令）、config（設定讀寫）、以及把 CBM 設定進 43 個 coding agent（Claude Code、Codex、OpenCode、Cursor、Gemini CLI…）。

1. 安裝 / 更新 / 移除

cbm_cmd_install / cbm_cmd_update / cbm_cmd_uninstall cli.c安裝生命週期的三個子指令。

更新刻意不做「in-process updater」——因為那結構上是「下載 + 解壓 + 標記執行 + 執行」，正是防毒軟體最警戒的 dropper 行為。所以 update 只驗證旗標、印出「重跑 install.sh」的指令，由外部指令碼完成實際替換（install.sh 是 idempotent，重跑就是更新）。

教學重點：安全設計 > 便利——這個決定換掉了「內建自動更新」換來「二進位裡沒有下載器特徵」。Windows 上更是硬性需求（執行中的 exe 無法自我替換）。

2. 43 個 agent 平台

agent 設定安裝 cli.c偵測已裝的 agent，寫入 MCP 設定 + 指令/skill/hook。

37 個自動偵測 + 6 個 conditional/explicit（有已存在的 config 路徑才寫）。每個平台寫入：MCP config、durable context（AGENTS.md / GEMINI.md 等）、skill、以及對應的 hooks。設計原則是絕不亂開實驗性 flag、不啟用 plugin、不信任第三方指令。

3. 三層 agent profile

Scout / Verify / Auditor cli.c為支援自訂 agent 的平台建立三個圖查詢 agent。

從一份 canonical contract 產生三層定義：

  • Scout（Tier 1）：3–4 個窄呼叫，快速試探性發現，不做 absence/impact/dead-code 聲稱。
  • Verify（Tier 2，預設）：任務導向的圖證據 + 精確原始碼檢查 + 引用路徑涵蓋。
  • Auditor（Tier 3）：受限範圍、完整分頁、更廣的關係檢查、明確的未解限制。

每層都批次呼叫 check_index_coverage 檢查證據路徑——clean 只代表「沒有記錄缺口」。

4. config 子指令

config set/get/list/reset cli.c讀寫 runtime 設定（auto_index、auto_watch、auto_index_limit…）。

設定存在 ${CBM_CACHE_DIR}/_config.db（SQLite）。例：config set auto_index true 讓新專案首次連線自動索引；auto_watch false 關掉背景 watcher 註冊。

看完這頁你應該能說出：為什麼 CBM 不用 in-process updater、43 個平台是「偵測 + conditional」而非全寫、Scout/Verify/Auditor 三層的職責差異、以及 config 存哪、auto_index 是做什麼。

教學解說

cli.c 處理 install/uninstall/update/config 等 43 個 client surface 的設定。這是 CBM 與各種 AI agent 平台整合的橋樑。

進階實戰 · 診斷「更新後 hooks 失效」

前面追蹤過 install 流程；現在反過來——功能壞了要怎麼診斷。情境：更新 CBM 後，某個平台的 hooks 不再把圖符號注入 context：

  1. 先查 config 現況：codebase-memory-mcp config list——確認 auto_index / auto_watch 等設定沒有被更新流程動到。
  2. 檢查 hooks 檔案：找到該平台的 config（如 ~/.claude.json），確認 hook 定義還在、路徑指向的 CBM 二進位是否存在。
  3. 檢查版本一致性：codebase-memory-mcp --version + cat ~/.cache/codebase-memory-mcp/logs/activation-events.ndjson——確認你跑的是不是新版本、activation 是否成功。
  4. 重跑 install 做 migration：codebase-memory-mcp install——migration 只覆寫 byte-identical 的先前定義；如果你的 hooks 被手動改過，它不會動它（這可能是「失效」的真相：版本格式變了但舊定義沒被更新）。
  5. 驗證：在 agent 裡觸發一次 Grep，確認 hook 是否注入 additionalContext。

為什麼選這條路徑：更新後「某個功能失效」的診斷，核心是分離「版本問題」與「設定問題」。先查 config（設定層），再查 activation（版本層），最後靠 migration 規則推斷「是不是我的定義被改過」。這條路徑避免了你直接刪掉設定重裝——那會丟掉你手動的客製化。

深入原理 · Installer 的寫入模型與「以為 re-install 會重置一切」的誤解

cli.c 的安裝是資料導向的：每個平台有一份描述（config 寫入位置 + context 檔 + skill + hooks）。install.sh 是 idempotent（重跑就是更新）。更新流程刻意不做 in-process updater——因為「下載 + 解壓 + 標記執行 + 執行」正是 dropper 特徵，防毒軟體會警戒；Windows 上執行中的 exe 也無法自我替換。config 存在 ${CBM_CACHE_DIR}/_config.db（SQLite）。

「大家以為正確其實有誤」的案例：很多人以為「re-run install 會把我的設定重置回預設」，所以更新後出問題不敢重跑。實際上 migration 的規則是只覆寫 byte-identical 的先前定義——只有「跟上一次我們寫的一模一樣」的檔案才會被換新；你手動改過的部分會被保留。所以「重跑 install」在大部分情況是安全且被推薦的補救手段，它不會抹掉你的客製化。

進階疑難排解

症狀可能原因解決方案
install 對某平台完全沒寫入該平台是 conditional，config 路徑不存在先安裝並使用該平台，再重跑 install
update 只印了一行指令設計如此——update 不做 in-process 替換照印出的指令重跑 install.sh（idempotent）
config set 不生效你改了 CBM_CACHE_DIR，讀到另一份 _config.db確認 cache root 一致，再重跑 config list 驗證
更新後 hooks 沒注入 context舊定義與新版格式不符，且你的定義被改過（非 byte-identical）還原定義或手動套用新格式後重跑 install
Windows 上更新失敗執行中的 exe 無法自我替換關閉所有 process 後，由外部 install.sh 完成替換

進階挑戰題

  1. 解釋「in-process updater」的 dropper 特徵是什麼——為什麼把它當成安全設計決策而非只是「懶得做」？
  2. 設計一個 install 的測試：如何驗證「conditional 平台在 config 不存在時不會被寫入、存在時才會」？（可參考 tests/ 的 test_cli.c 風格）
  3. 「migration 只覆寫 byte-identical 定義」這條規則，對「使用者客製化」與「官方更新」兩者分別的利弊是什麼？
