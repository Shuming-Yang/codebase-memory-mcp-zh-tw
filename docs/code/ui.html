ui/ — 3D 圖形界面

嵌入式 HTTP server + 3D graph visualization
目錄：src/ui/（httpd.c + http_server.c + layout3d.c + config.c）

大方向

ui/ 是「--ui 變體」的內建 3D 圖形界面：一個嵌入式 HTTP server 服務前端（graph-ui/，React + three.js），提供 localhost:9749 的互動知識圖譜瀏覽器。UI 由共享 daemon 擁有——並行 session 不會開重複的 HTTP server。

1. HTTP server

httpd.c · http_server.c ui/嵌入式 HTTP server：靜態資源 + JSON API。

提供前端 bundle（embedded assets）與圖資料 API（節點/邊/社群、搜尋、POST /api/index）。上游特別註明 HTTP server 是第一方實作——沒有用第三方 HTTP library。

2. 3D 佈局

layout3d.c ui/3D 力導向佈局的圖側計算。

前端用 three.js 渲染，但節點的初始 3D 座標由 C 側算好（layout3d.c），前端直接吃座標做 physics。跨 repo 時用 multi-galaxy 佈局呈現不同 repo 的「星系」。

3. 設定與嵌入

config.c · embedded_assets.h ui/UI 設定與前端 bundle 嵌入。

config.c 管 ui_enabled / ui_port（存在 cache 的 config.json）；embedded_assets.h 把建置好的 graph-ui 前端編進二進位（非 --with-ui 的 lean build 用 embedded_stub.c）。

看完這頁你應該能說出：UI 是嵌入式 HTTP server + 前端、3D 座標由 C 側預算好、UI 由 daemon 共享避免重複 server、以及 lean vs ui 兩種 build 的差別。

教學解說

ui 模組提供嵌入式 HTTP server + 3D 圖形界面（localhost:9749）。這是 CBM 的視覺化入口。

Worked Example

啟動並使用 3D UI：

# 1. 啟動 UI
codebase-memory-mcp --ui

# 2. 開啟瀏覽器
open http://localhost:9749

# 3. 在 UI 中探索圖結構

進階實戰 · 追蹤 UI 的資料從 store 到 three.js

你在瀏覽器看到 3D 圖，資料是怎麼流過去的？以「開啟 --ui、瀏覽一個專案」為例：

  1. 啟動：codebase-memory-mcp --ui 啟動嵌入式 HTTP server（httpd.c / http_server.c，第一方實作、無第三方 HTTP library）於 localhost:9749——UI 由共享 daemon 擁有，並行 session 不會開重複 server。
  2. 前端載入：瀏覽器請求前端 bundle——它編譯進二進位（embedded_assets.h，graph-ui/ 的 React + three.js build）。
  3. 資料 API：前端向 httpd 要圖資料（節點/邊/社群、搜尋）——search_code(project="cbm", pattern="/api/") 找這些 endpoint。
  4. 3D 座標：節點的初始 3D 座標由 C 側 layout3d.c 預先算好，前端直接吃座標做 physics 渲染——跨 repo 時用 multi-galaxy 佈局呈現不同 repo 的「星系」。

為什麼選這條路徑：UI 不是「另一個獨立 app」，而是「一個編進二進位的嵌入式 server + 內建前端」。追蹤這條資料流，你才能診斷「白屏 / 資料不顯示 / 佈局怪異」這類問題該往哪層找。

深入原理 · 嵌入資產與 lean/ui 兩種 build

前端是 React + three.js，但被編譯成靜態資產嵌進二進位（embedded_assets.h）——所以 CBM 單一二進位就能提供完整 UI，不必在目標機上另裝 node_modules。config.c 管 ui_enabled / ui_port（存在 cache 的 config.json）。--with-ui 的完整 build 嵌入前端；lean build 用 embedded_stub.c 頂替（沒有 UI 但有全部 CLI/MCP 功能）。3D 佈局分兩段：C 側算初始力導向座標（layout3d.c），前端跑互動 physics。

「大家以為正確其實有誤」的案例：很多人以為「3D 渲染與佈局全是前端 three.js 算的」，於是調整 UI 問題時全在瀏覽器 devtools 裡找。實際上初始座標由 C 側預算——節點「一開始長在哪」由 layout3d.c 決定，前端只負責物理模擬與渲染。所以「佈局很奇怪」或「跨 repo 星系沒分開」這類問題，可能要改 C 側的佈局邏輯，而不是前端 CSS。另一個常見誤解：lean build 跑 --ui 沒反應，被當成「bug」——其實是該 build 沒有嵌入 assets（embedded_stub），屬於預期行為。

進階疑難排解

症狀可能原因解決方案
--ui 啟動後白屏lean build 未嵌入前端 assets用 --with-ui build 或官方 release
port 9749 被佔用另一個 process 佔住改 ui_port；或關閉佔用程序
UI 卡頓節點數過多，前端渲染過載用社群聚合檢視；或縮小檢視範圍（filter by label）
跨 repo 沒分開成星系multi-galaxy 佈局依賴跨 repo 節點資料確認多個 project 有 index 進同一 cache；重開 UI
UI 連不到 daemondaemon 沒跑或 endpoint 失效先啟動一個 session 讓 daemon 起來，再開 UI

進階挑戰題

  1. 解釋「前端編譯進二進位（embedded_assets.h）」對部署的意義——對比「另外用 npm 部署前端」的做法。
  2. 設計一個 multi-galaxy 佈局：假設 3 個 repo，你怎麼決定「哪些節點分到哪個星系、星系間怎麼擺」？
  3. 「C 側預算初始座標、前端跑 physics」的分工，對「大圖效能」的意義是什麼？如果把全部分散到前端會怎樣？
