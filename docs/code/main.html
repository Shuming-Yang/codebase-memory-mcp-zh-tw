main.c — 單一二進位入口

一個二進位，MCP server / CLI / install / update / config 全包
檔案：src/main.c（2,418 行）

大方向

main.c 是整個二進位的入口。它根據第一個參數決定進入哪個模式：無參數 → MCP stdio server；cli → 單次指令；install/update/uninstall/config → 安裝與設定子指令。設計哲學是單一靜態二進位：不另外帶 companion executable。

1. 模式分派

main() main.c依 argv[1] 決定 MCP / CLI / install 模式。

開頭先做基礎初始化（記憶體、log、平台抽象），然後分派：

  • 無參數或 stdio → MCP server（mcp/mcp.c）
  • cli → 單次 CLI 指令（不啟動 daemon）
  • install / update / uninstall / config → cli/cli.c
  • --ui=true → 啟動 3D UI（ui/）

2. 與 daemon 的關係

MCP 模式的 daemon 連線 main.cMCP 模式啟動或連上 per-account daemon。

MCP 模式不是自己包辦一切：它透過 daemon（daemon/）共享 watcher、索引 job、UI。第一個 daemon-backed session 啟動 daemon，最後一個 session 關閉它。CLI 模式刻意分離——單次指令不啟動 daemon、不留常駐 process。

3. 維持 stdout 乾淨

log 路由 main.c日誌走 stderr / daemon log，stdout 只留 MCP JSON-RPC。

MCP 是 stdio 協議：stdout 只能有 JSON-RPC，混入任何日誌都會讓 client 解析失敗。所以日誌被導到 stderr（session 層）或 ${CBM_CACHE_DIR}/logs/cbm-daemon.log（daemon 層）。--progress 只寫 stderr，讓 pipe/script 保持機器可讀。

看完這頁你應該能說出：單一二進位的分派邏輯、MCP 模式如何跟 daemon 合作共享資源、CLI 模式為何刻意不啟動 daemon、以及 stdout 乾淨對 MCP 協議的重要性。

教學解說

main.c 是 CBM 的單一二進位入口——所有功能（MCP server、CLI、install/update/config）都從這裡分派。理解 main.c 就理解了 CBM 的啟動流程。

進階實戰 · 除錯「MCP client 收到混亂輸出」

MCP 是 stdio 協議，stdout 只能有 JSON-RPC。如果你的 agent 一直報「protocol error / parse failure」，這條路徑幫你定位：

  1. 先確認 stdout 是不是真的髒了：codebase-memory-mcp 2>/dev/null | head -c 500——若出現日誌文字而非 JSON-RPC，就是 log 沒走對通道。
  2. 檢查 log 路由：main.c 把日誌導向 stderr（session 層）或 ${CBM_CACHE_DIR}/logs/cbm-daemon.log（daemon 層）——兩個地方都不該碰 stdout。
  3. 檢查是不是 CLI 模式在搞鬼：CLI 模式的 --progress 只寫 stderr、stdout 保持機器可讀；確認你的 script 沒有把 stderr 併進 stdout（2>&1 是常見元兇）。
  4. 確認 daemon 連線正常：MCP 模式會啟動或連上 daemon；若 daemon 啟動失敗，log 會漏到錯誤地方。

為什麼選這條路徑：「stdout 乾淨」是 MCP 的生存條件——混入一行日誌，整個 JSON-RPC 串流就壞了。這條路徑教你先把「輸出通道」和「log 通道」分開診斷，而不是去懷疑查詢邏輯。

深入原理 · 單一二進位的分派與「以為 CLI 模式會啟動 daemon」的誤解

main() 開頭做平台初始化（記憶體/log/threads），然後依 argv[1] 分派：無參數或 stdio → MCP server；cli → 單次指令（不啟動 daemon、不留常駐 process）；install/update/uninstall/config → cli.c；--ui=true → 3D UI。這一切都是單一靜態二進位——沒有 companion executable，所有模組編在一起。

「大家以為正確其實有誤」的案例：cli 指令執行時，log 也走 stderr——但很多人用 cli search_graph 2>&1 | jq 這類寫法把 stderr 併入，結果 JSON 前面多了一堆 log 行，jq 直接掛掉。這不是 CBM 的 bug，而是「2>&1 破壞了 stdout/stderr 分離」的慣用寫法問題。另一種誤解是「CLI 模式與 MCP 模式共用同一份圖資料，所以 CLI 跑完 MCP 一定看得到」——它們共享 SQLite 與 per-project lock，但 CLI 不會觸發 watcher，所以你 CLI 手動改了 repo，MCP 側要等 watcher 增量才看到新圖。

進階挑戰題

  1. 解釋「stdout 只能有 JSON-RPC」對 MCP 協議的意義——如果違反，client 端會發生什麼（用協議解析的視角）。
  2. 設計一個分派測試：給定不同的 argv[1]，驗證 main() 進入正確的模式（參照 test_main 風格）。
  3. 「CLI 模式不啟動 watcher」這個設計決策，對「CI 腳本裡跑 cli 查詢」的情境有什麼影響？你會怎麼在 CI 裡保證圖是新鮮的？
