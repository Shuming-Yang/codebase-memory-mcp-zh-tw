程式碼對照

純 C 源碼逐函數講解——每個函數一個收縮塊，中文解說配英文原始碼

codebase-memory-mcp 是純 C（約 13 萬行），不像 graphify（Python）那樣好讀。這裡挑「最高教學價值」的模組逐函數講解。所有行數為對齊版 main @ 2c50c77 實測。

main.c單一二進位入口：MCP stdio server + CLI + install/update/config 的分派。 mcp/mcp.c15 個 MCP 工具註冊、JSON-RPC 2.0、session detection、auto-index。 store/store.cSQLite 節點/邊/遍歷/搜尋/Louvain 社群偵測。 cypher/cypher.copenCypher 唯讀子集的 lexer→parser→planner→executor。 cli/cli.cinstall/uninstall/update/config、43 個 client surface、hook 安裝。 pipeline/多 pass 索引的調度（pipeline.c + registry.c）。 pipeline/pass_*.c各 pass 職責：parallel/pkgmap/lsp_cross/semantic_edges/cross_repo/infrascan/route_nodes… daemon/會話協調 daemon、IPC、admission barrier、lifecycle。 discover/檔案發現：.gitignore → .cbmignore → symlink 處理。 semantic/語意搜尋：nomic-embed-code（768d int8）、11-signal scoring、MinHash/ROTSQ。 ui/3D 圖形 UI、embedded assets、HTTP server（localhost:9749）。 tests/6,768 tests / 120 suites 測試策略、fixtures、grammar_cases。
全站已建置：12 個程式碼對照頁全部完成（對齊上游 main @ 2c50c77）。建議閱讀順序：main → mcp → store → cypher → cli。

進階實戰 · 用知識圖譜導航 CBM 源碼——追蹤 auto_index

閱讀順序是「線性」的；但「某個功能從入口到落地」的路徑是跨模組的。以「新 session 連線時自動索引」（auto_index）為例，用 CBM 自己導航自己：

  1. 找 config 的開關：search_graph(project="cbm", query="auto_index config", label="Function")——先在 cli/config 相關函式裡找到 auto_index 的讀取點。
  2. 找 MCP 層的觸發：search_graph(project="cbm", name_pattern=".*auto_index.*", label="Function")——mcp.c 裡 session 初始化會檢查該設定。
  3. 跨模組追蹤：trace_path(function_name="cbm_mcp_auto_index", direction="outbound")——看它怎麼把索引請求丟給 daemon 的 application job。
  4. 落地到 pipeline：trace_path(function_name="cbm_pipeline_run", direction="outbound")——最後是 pipeline 的 pass 串。

為什麼選這條路徑：auto_index 這個功能跨越 cli（設定）→ mcp（觸發）→ daemon（排程）→ pipeline（執行）四個模組。用 search_graph 找起點、trace_path 沿 CALLS 邊跨檔走，比人工在 13 萬行 C 裡跳轉快得多——這正是「用圖導航大型 C codebase」的實戰示範。

深入原理 · 單一二進位 + arena 記憶體 + 可測試性鉤子

讀 CBM 源碼前，先建立三個背景知識：（1）單一靜態二進位——所有模組編進一個 binary，main() 依參數分派，無 companion executable；（2）foundation/ 的平台抽象——arena 記憶體（批次分配、批次釋放，配合 RAM-first 管線）、執行緒、檔案系統、regex 都被抽象化，所以測試可以注入 fake；（3）可測試性設計——大量函式有 _for_test() 鉤子（如 set_before_publish_hook_for_tests），讓測試能注入失敗/延遲。

「大家以為正確其實有誤」的案例：在大型 C 專案裡用 search_graph(name_pattern=".*parse.*") 搜「parse」，會回傳幾十個 parse_* 函式（JSON parse、Cypher parse、AST parse…）。很多人直接抓第一個就往下追，結果追錯檔案。正確做法是同時用 label + file_pattern 縮小（如 file_pattern="src/cypher"），並用 get_code_snippet 確認 qualified name 的 path_parts——「搜到函式」不等於「搜到你要的那個函式」。

進階疑難排解

症狀可能原因解決方案
search_graph 回傳太多同名函式沒帶 label 與 file_pattern加 label=Function + file_pattern 縮小範圍
trace_path 追到一半斷掉該語言（或該模式）解析 fallback 到 USAGE斷點處改查 USAGE/CALL_REFERENCE，或讀 get_code_snippet 人工接
行數對不上文件你的 checkout 與對齊版 main@2c50c77 不同切到對應 commit 再看行數
找不到 auto_index 相關函式名稱不是 auto_index 開頭（可能是 mcp.c 內部 static）用 query 全文搜尋（BM25）而非 name_pattern
讀到一半不知這函式被誰用只做了 outbound 追蹤補 trace_path(direction="inbound") 看 caller

進階挑戰題

  1. 追蹤「cli search_graph 從 main() 到 store 的完整路徑」——把每一跳的函式名寫出來。
  2. 用 get_code_snippet 讀 cbm_pipeline_run 的開頭，說明它如何初始化 pipeline 並決定跑哪些 pass。
  3. 解釋 _for_test() 鉤子如何讓「注入失敗」成為可能——這對 6,768 個測試的意義是什麼？
