cypher/cypher.c — 查詢引擎

openCypher 唯讀子集的 lexer → parser → planner → executor
檔案：src/cypher/cypher.c（4,972 行）· cypher.h

大方向

cypher.c 是一個迷你的資料庫查詢引擎：它把 query_graph 收到的 Cypher 字串編譯成可執行的計畫，再對 store 執行。雖然只支援 openCypher 的唯讀子集，但完整的四階段（lexer → parser → planner → executor）都有——讀這個檔案等於讀「怎麼在 C 裡寫一個小型圖查詢引擎」。

1. 前端：lexer + parser

lexer（tokenize） cypher.c把查詢字串切成 token：識別字、label、邊方向、數字、字串。

把 MATCH (f:Function)-[:CALLS]->(g) RETURN g.name 切成 token 序列。處理 : label、[*1..3] 可變長度、引號字串、=~ regex 等。

parser（AST 建立） cypher.c把 token 組合成語法樹：MATCH/WHERE/RETURN 子句。

遞迴下降解析：pattern（節點、邊、方向）、WHERE 條件樹、aggregates、UNION。遇到不支援的子集語法（MERGE、CALL、comprehensions）在此回報 unsupported … 錯誤。

2. Planner + Executor

planner cypher.c把 AST 轉成執行計畫（哪些邊先走、filter 順序）。

決定查詢順序：先抓 label 少的候選，再做 join/filter。EXISTS 子查詢（死碼偵測）被編譯成「檢查單跳存在性」的特別步驟。

executor（cbm_cypher_execute） cypher.c執行計畫，回傳 cbm_cypher_result_t。

對 store 的 SQL 下查詢、組列、套 aggregates（count/sum/avg/min/max/collect）、處理 ORDER BY / SKIP / LIMIT、UNION 合併。<1ms 的 Cypher 查詢就在這裡達成。

看完這頁你應該能說出：Cypher 子集是「四階段編譯」的小型查詢引擎、lexer/parser/planner/executor 各做什麼、unsupported … 在哪一層被拒絕、以及 EXISTS 子查詢如何編譯成單跳存在性檢查。

教學解說

cypher.c 實現了 openCypher 唯讀子集的完整編譯器：lexer → parser → planner → executor。這是 CBM 最複雜的模組之一。

Worked Example

追蹤 Cypher 查詢的執行流程：

# 1. 找到 lexer 入口
search_graph(project="cbm", name_pattern=".*cypher_lex.*", label="Function")

# 2. 找到 planner
search_graph(project="cbm", name_pattern=".*cypher_plan.*", label="Function")

# 3. 找到 executor
search_graph(project="cbm", name_pattern=".*cypher_exec.*", label="Function")

# 4. 追蹤完整流程
trace_path(project="cbm", function_name="cypher_execute", direction="both")

進階實戰 · 追蹤一個查詢從 lexer 到 executor 的完整旅程

四階段引擎最好的學習方式，是拿一個真實查詢逐層拆解：MATCH (f:Function)-[:CALLS]->(g) WHERE g.name = 'main' RETURN f.name LIMIT 5

  1. lexer：search_graph(project="cbm", name_pattern=".*cypher_lex.*", label="Function") 找到 tokenizer——它把字串切成 MATCH、(、f、:、Function、-、[:、CALLS、->…等 token，處理 label、引號、[*1..3]、=~。
  2. parser：search_graph(project="cbm", name_pattern=".*cypher_parse.*", label="Function")——遞迴下降把 token 組合成 AST（pattern 節點/邊、WHERE 條件樹）。子集外的語法（MERGE、comprehension）在此層就回報 unsupported。
  3. planner：search_graph(project="cbm", name_pattern=".*cypher_plan.*", label="Function")——決定先抓哪個 label 的候選集、filter/join 順序。
  4. executor：search_graph(project="cbm", name_pattern=".*cypher_exec.*", label="Function")——對 store 下 SQL、組列、套 aggregate、處理 LIMIT。

為什麼選這條路徑：與其背四階段的名詞，不如用「一個查詢在 cypher.c 裡的每一站長什麼樣」來建立直覺。每站對應一組函式，search_graph 直接帶你到原始碼，這比讀整個 4,972 行檔案有效。

深入原理 · 遞迴下降解析與「以為 unsupported 是執行期才報錯」的誤解

parser 是遞迴下降的：pattern、WHERE 條件、aggregates、UNION 各有對應的解析函式，遇到不認識的關鍵字就往「不支援」分支丟。unsupported … 錯誤因此是編譯期（parse 層）就決定的，而不是等 executor 跑起來才失敗——所以你在任何查詢之前就能確定「這句寫不寫得過」，錯誤訊息也刻意給得明確（unsupported syntax: MERGE 之類）而不是回空結果。executor 只負責執行「已通過編譯」的計畫。

「大家以為正確其實有誤」的案例：有人拿到 unsupported … 後去調整「查詢邏輯」或「資料」——其實問題在語法層，與圖內容無關。另一個常見誤解是「WHERE 的寫法順序決定執行順序」——planner 會重新排序（先抓 label 少的候選集），所以你看到「慢的寫法」和「快的寫法」產出相同結果，但效能差很多。

進階疑難排解

症狀可能原因解決方案
查詢報 unsupported syntax用了子集外的關鍵字/語法在 parser 層確認支援清單；改寫成唯讀子集
同樣查詢在不同專案速度差很多planner 選的候選集大小不同（label 多寡）加更嚴格的 label/WHERE 前置過濾縮小候選集
結果順序每次不同沒寫 ORDER BY，SQL 回傳順序不保證加上 ORDER BY 再套 LIMIT
aggregate 結果不直覺count 沒有 DISTINCT，或 join 產生了重複列用 count(DISTINCT …) 或先 WITH DISTINCT 再聚合
自己改 cypher.c 後查詢掛掉改了引擎，卻沒跑測試跑 scripts/test.sh --suites cypher（本機過 = CI 過）

進階挑戰題

  1. 描述「新增一個 reduce() 函式」需要動 lexer/parser/planner/executor 的哪些位置，並指出哪一層最容易被忽略。
  2. 寫出「MATCH (a)-[:CALLS*1..3]->(b) 中，planner 如何決定先從 a 還是 b 開始展開」的判斷準則。
  3. 解釋為什麼「unsupported 在 parse 層回報」對使用者體驗是加分——對比「靜默回空」的壞處。
