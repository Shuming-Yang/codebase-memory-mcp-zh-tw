Team-Shared Graph Artifact

commit 一個壓縮檔，隊友 clone 免重 index

一句話

把單一壓縮檔 commit 進你的 repo，隊友 clone 下來第一次跑 CBM 就直接載入圖，不必重跑完整索引。

它是什麼

.codebase-memory/graph.db.zst 是知識圖譜的 zstd 壓縮快照（SQLite DB、index 剝離、VACUUM INTO 壓實、zstd 壓縮，典型 8–13:1）。住在你 source 旁邊：

  • 你 index 時，artifact 被寫出或更新。
  • 隊友 clone 後第一次跑 CBM，artifact 被解壓 + 增量索引補上 local diff。

兩種 tier

Tier做法何時
Bestzstd -9 + index 剝離 + VACUUM INTO明確呼叫 index_repository 時
Fastzstd -3watcher 做低延遲增量更新時

Bootstrap

本機沒有 DB 但 artifact 存在時，index_repository 先匯入 artifact，再跑增量索引——省掉完整重索引的成本。

無 merge 痛

首次 export 時自動建立 .gitattributes 的 merge=ours，並行編輯不會在二進位 artifact 上產生衝突。

可選

不 commit 也行：把 .codebase-memory/ 加進 .gitignore 就大家都重新索引。結果在精神上類似 graphify 的 graphify-out/，但是單一壓縮檔 + 明確兩層 export + 完整性檢查 + 零 merge 摩擦。

看完這頁你應該能說出：graph.db.zst 是什麼、Best/Fast 兩 tier 何時用、bootstrap 如何省掉重索引、merge=ours 為什麼讓二進位不衝突、以及不想共享時怎麼關。

教學解說

Graph Artifact 讓團隊共享知識圖譜——把壓縮的 SQLite DB commit 進 repo，隊友 clone 後第一次跑 CBM 就直接載入，不必重跑完整索引。這對大型專案特別有價值（Linux kernel 全索引要 3 分鐘）。

關鍵設計：two-tier export（Best 品質用 zstd -9 + VACUUM；Fast 用 zstd -3 低延遲）+ merge=ours（gitattributes 自動設定，並行編輯不衝突）。

Worked Example

團隊共享 graph artifact 的工作流：

# 1. 你的機器：索引並匯出 artifact
codebase-memory-mcp cli index_repository --repo-path ~/my-project
# → 自動產生 .codebase-memory/graph.db.zst

# 2. 確認 artifact 存在
ls -la .codebase-memory/
# → graph.db.zst（典型 8-13:1 壓縮比）

# 3. Commit 進 repo
git add .codebase-memory/ .gitattributes
git commit -m "chore: add CBM graph artifact for team sharing"

# 4. 隊友 clone 後：
git clone https://github.com/team/project.git
codebase-memory-mcp cli index_repository --repo-path ~/project
# → 自動 bootstrap：解壓 artifact → 增量索引補上 diff

常見錯誤 / 診斷

症狀原因解法
artifact 解壓失敗CBM 版本不一致（artifact 是舊版產生的）確認所有人用相同 CBM 版本
git merge 衝突.gitattributes 的 merge=ours 未生效確認 .gitattributes 存在且有 merge=ours 設定
artifact 太大大型專案或未壓縮用 Best tier（zstd -9 + VACUUM）重新匯出

進階實戰 · 10 人團隊的大型 monorepo 的 artifact 策略

單一 repo 的手把手共享很簡單；10 人團隊 + 大型 monorepo 時，誰產 artifact、什麼時候產、用哪個 tier，需要一個策略：

  1. 決定哪些場景需要 artifact：monorepo 全索引可能 10+ 分鐘——只有「首次 clone 的 onboarding」值得吃這成本，日常開發靠增量 watcher。
  2. CI 統一產出 Best tier：在 merge 到 main 的 pipeline 上跑 index_repository --repo-path . --persistence，把 .codebase-memory/graph.db.zst（zstd -9 + VACUUM + index 剝離）commit 回 main。這保證 artifact 永遠是「最新 main」的圖。
  3. 隊友 onboarding：clone 後第一次 index_repository 自動 bootstrap（解壓 + 增量補 local diff），幾分鐘內就有完整圖。
  4. 保留 .gitattributes 的 merge=ours：確保並行開發時 artifact 的 git merge 不會炸出 binary 衝突。

為什麼選這條路徑：把「每次每個人都全量索引」的 O(人數 × 專案大小) 成本，變成「CI 一次 + 每人一次解壓」。對於 onboard 新人的體驗，從「等 10 分鐘」變成「等 10 秒」。Fast tier 留給 watcher 的低延遲增量，不在這條策略路徑上。

深入原理 · artifact 的壓縮管線與「以為 merge=ours 會合併」的誤解

graph.db.zst 不是簡單的「zip 一個 SQLite 檔」：Best tier 的管線是（1）剝離索引結構，（2）VACUUM INTO 把 DB 壓實成乾淨副本，（3）zstd -9 壓縮，典型 8–13:1；Fast tier 則直接 zstd -3 以換取低延遲。bootstrap 時先做完整性檢查，再解壓、再跑增量索引補上與 artifact 之間的 diff。整個設計刻意避免「整包重新索引」。

「大家以為正確其實有誤」的案例：.gitattributes 的 merge=ours 名字裡有「merge」，很多人以為它會「把兩邊的內容合併起來」或「保留對方最新版」。實際上 merge=ours 的意思是：merge 時永遠保留「我方」（目前分支）的版本，對方分支對這個檔的變更會被直接丟棄。這對「二進位、無法 diff 的圖快照」是正確的——你永遠要的是 main 上 CI 產的版本，而不是 feature 分支上亂產的版本。誤解它的人會在 feature 分支也手動重產 artifact，結果 merge 後圖反而被舊版覆蓋。

進階疑難排解

症狀可能原因解決方案
隊友 bootstrap 後缺某些檔案artifact 是較舊 generation，本地新增檔案未被涵蓋讓本地 watcher 或一次 index_repository 跑完增量補上
解壓或完整性檢查失敗artifact 由不同 CBM 版本或損壞的 commit 產生全員升級到同一版本；刪掉舊 artifact 重新 export
merge 時 binary 衝突merge=ours 未寫入 .gitattributes，或路徑規則不符確認 .gitattributes 存在且 pattern 正確（如 .codebase-memory/** merge=ours）
artifact 越推越大長期未 VACUUM，或塞入了大量歷史垃圾用 Best tier 重新 export（VACUUM INTO 會壓實）
feature 分支把 artifact 改成舊版有人手動在分支上重產了 artifact在 CI 只允許 main 產 artifact；教團隊「不要手動產、不要手動 merge artifact」

專案級端到端 Worked Example — 10 人團隊的 artifact 策略

假設你的 10 人團隊共用一個大型 monorepo，要建立 artifact 共享策略。

  1. CI 統一產出 Best tier：在 merge 到 main 的 pipeline 上跑 index_repository --repo-path . --persistence，把 graph.db.zst（zstd -9 + VACUUM）commit 回 main。
  2. 隊友 onboarding：clone 後第一次 index_repository 自動 bootstrap（解壓 + 增量補 local diff）。
  3. 保留 .gitattributes：確保 merge=ours 設定存在，並行開發時 artifact 不會衝突。
  4. 版本管理：全員升級到同一 CBM 版本——artifact 由不同版本產生會導致解壓失敗。
  5. 監控 artifact 大小：長期未 VACUUM 會讓 artifact 越推越大——定期用 Best tier 重新 export。
