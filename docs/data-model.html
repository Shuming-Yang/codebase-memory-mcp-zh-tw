圖資料模型

13 種節點 label、23 種邊型、qualified name

節點 Label

Project · Package · Folder · File · Module · Class · Function · Method · Interface · Enum · Type · Route · Resource
Label意義
Project一個被索引的 repo（含 repo_path、generation）
Package / Module套件/模組（套件解析自 package.json / go.mod / Cargo.toml…）
Folder / File目錄與檔案
Class / Interface / Enum / Type型別定義
Function / Method可呼叫物
RouteREST 端點（HTTP method + path）
ResourceIaC 資源（K8s kinds 等）

邊型

邊意義
CONTAINS_PACKAGE/FOLDER/FILE容器關係
DEFINES / DEFINES_METHOD定義關係
IMPORTS匯入
CALLS呼叫（型別解析後的呼叫邊）
CALL_REFERENCE可呼叫值在支援的 reference site 使用、解析到單一目標
USAGE識別字被用，但無法證明唯一目標（含歧義/複雜運算式）
HTTP_CALLS / ASYNC_CALLS跨服務呼叫
IMPLEMENTS / INHERITS實作/繼承
HANDLESRoute → handler 的對應
EMITS / LISTENS_ONchannel（Socket.IO、EventEmitter、pub-sub）
DATA_FLOWS資料流（arg-to-param 對應 + field access chain）
SIMILAR_TOMinHash + LSH 近複製（Jaccard 計分）
SEMANTICALLY_RELATED詞彙不匹配、同語言、score ≥ 0.80 的語意關係
CONFIGURES / WRITES / MEMBER_OF / TESTS / USES_TYPE / FILE_CHANGES_WITH其餘語意邊
為什麼要分 CALLS / CALL_REFERENCE / USAGE：這三種「看起來都是呼叫」的邊，代表不同程度的解析確定性。型別解析成功且唯一 → CALLS；可呼叫值引用但只是當參數傳遞 → CALL_REFERENCE；無法證明唯一目標 → USAGE。這是 CBM 比單純 grep 強的地方——它不硬猜。

Qualified Name

get_code_snippet 用 qualified name 定位：

<project>.<path_parts>.<name>

例如: myproj.src.services.order.process_order

先用 search_graph 發現確切名稱，再餵給 get_code_snippet。

查詢範例

資料模型 + Cypher 的威力（Cypher 全解）：

// 死碼偵測：沒有被任何 CALLS 指向的函式
MATCH (f:Function)
WHERE NOT EXISTS { (f)<-[:CALLS]-() }
RETURN f.name

// main 呼叫了誰
MATCH (f:Function)-[:CALLS]->(g)
WHERE f.name = 'main'
RETURN g.name

跨 repo

多個 repo index 進同一個 store 時，會產生 CROSS_* 邊連結跨 repo 節點，3D UI 用 multi-galaxy 佈局呈現跨 repo 架構。詳見 Multi-Agent 與 get_architecture。

看完這頁你應該能說出：CALLS / CALL_REFERENCE / USAGE 的差異、Route 與 Resource 節點各代表什麼、qualified name 的格式、以及如何用 Cypher 的 NOT EXISTS 找死碼。

教學解說

CBM 的圖資料模型有 13 種節點 label（Project → Function → Route → Resource）和 23 種邊型。理解這個模型是使用 Cypher 查詢的基礎。

最重要的概念是 CALLS / CALL_REFERENCE / USAGE 三種邊的差異：它們都代表「看起來像呼叫」的關係，但解析確定性不同。CALLS 代表型別解析成功且唯一；CALL_REFERENCE 代表可呼叫值引用但只是當參數傳遞；USAGE 代表無法證明唯一目標。這是 CBM 比 grep 強的地方——它不硬猜。

Worked Example

用資料模型 + Cypher 做架構分析：

-- 1. 找出所有 Route 節點及其 handler
MATCH (r:Route)-[:HANDLES]->(h:Function)
RETURN r.method, r.path, h.name
ORDER BY r.method, r.path

-- 2. 找出哪個套件有最多函式（模組複雜度）
MATCH (p:Package)-[:CONTAINS_FILE]->(f:File)-[:DEFINES]->(func:Function)
RETURN p.name, count(func) AS func_count
ORDER BY func_count DESC
LIMIT 10

-- 3. 找出跨套件的呼叫（耦合度分析）
MATCH (caller:Function)-[:CALLS]->(callee:Function)
WHERE caller.file_path CONTAINS '/auth/' AND callee.file_path CONTAINS '/order/'
RETURN caller.name, callee.name

-- 4. 找出未被使用的型別（可能是死碼）
MATCH (t:Type)
WHERE NOT EXISTS { (t)<-[[:USES_TYPE]]-() }
  AND NOT EXISTS { (t)<-[[:DEFINES]]-() }
RETURN t.name, t.file_path

進階實戰 · 追蹤「看起來被呼叫、其實只是被當參數傳遞」的案例

資料模型最有價值的地方，是它把「引用」的確定性分了等級。現在實戰追蹤一個真實的混淆案例：

  1. 先用 get_graph_schema(project="my-project") 看這個專案到底產出了哪些邊型——先看模型再問問題。
  2. 選一個函式，列出它所有的 inbound 邊：query_graph --query "MATCH (n)<-[r]->(f:Function) WHERE f.name = 'execute' RETURN type(r), count(*) ORDER BY count(*) DESC"。
  3. 如果結果同時出現 CALLS 與 CALL_REFERENCE：前者代表「真的呼叫了它」，後者代表「把它當 callback/參數傳給別人」——兩者語意完全不同，卻常被混為一談。
  4. 若出現大量 USAGE，代表型別解析無法證明唯一目標（動態分派、duck typing），此時不要據此斷言「誰呼叫了它」。
  5. 再補一個近複製檢查：query_graph --query "MATCH (a)-[:SIMILAR_TO]->(b) WHERE a:Function AND b:Function RETURN a.name, b.name, a.file_path"，找出被 copy-paste 的 handler。

為什麼選這條路徑：直接問「誰呼叫了 X」的人，會把 CALL_REFERENCE 和 USAGE 當成 CALLS，得到錯誤的影響範圍。這條路徑先「看 schema」再「分邊型」再「下結論」，是避免被資料模型誤導的標準做法。

深入原理 · SQLite 儲存格式與「以為 qualified name = 檔案路徑」的誤解

圖資料不是存在某個特殊「圖資料庫」裡，而是SQLite 正規化表格：節點表、邊表、屬性表（屬性以 JSON 存放），搜尋走 FTS5 全文索引並配上自訂的 cbm_camel_split tokenizer（讓 ProcessOrder 可被 process order 搜到）。Louvain 社群與 BFS 遍歷是應用層演算法，跑在 SQL 之上——所以 store 的查詢延遲依賴於 SQL 的 index 設計與批次技巧，而不是依賴某種神奇的圖引擎。

「大家以為正確其實有誤」的案例：qualified name 的格式是 <project>.<path_parts>.<name>，於是很多人以為「get_code_snippet 一定等於沿著檔案路徑找定義」。但當程式裡有同名函式（不同檔案、不同套件）或 macro 展開、generated code 時，qualified name 會因為 path_parts 的來源不同而產生你猜不到的名稱。正確做法永遠是：先用 search_graph 取得確切的 qualified_name，再餵給 get_code_snippet——自己拼字是最常見的錯誤來源。

進階疑難排解

症狀可能原因解決方案
找不到某個 Type/Interface 節點該語言沒有 type 抽取，或定義在未索引的檔案用 check_index_coverage 確認檔案進圖；查語言支援範圍
同名函式只查到一個search_graph 結果被 limit 截斷，或兩個名稱被合併用 file_pattern + 分頁（offset/limit）逐頁確認
全圖沒有 SIMILAR_TO 邊fast index 模式不跑 similarity，或 minhash 門檻太高用 full/moderate 模式重 index；調低相似度門檻
邊型清單與文件「23 種」不符不同索引模式/版本產出的邊型不同以 get_graph_schema 的實際輸出為準，不要對照死表格
qualified name 一直 not found自己拼了 path，少了 project prefix 或大小寫不符一律先 search_graph 拿官方名稱

進階挑戰題

  1. 用 get_graph_schema 列出某專案實際存在的所有邊型，並把每一種分類成「高確定性 / 中確定性 / 低確定性」。
  2. 設計一條查詢，找出「被 copy-paste 過且兩個副本都在同一套件」的函式對（結合 SIMILAR_TO 與 file_path）。
  3. 解釋為什麼「CALL_REFERENCE 被當成 CALLS」會造成錯誤的影響範圍分析，並寫出能區分兩者的查詢。

專案級端到端 Worked Example — 用資料模型做完整的架構健康檢查

假設你接手一個 Python FastAPI 專案，要用資料模型做完整的架構健康檢查。

  1. 先看 schema：get_graph_schema(project="fastapi-project")——確認實際產出了哪些 label 和邊型。
  2. 邊型分類：高確定性（CALLS、HANDLES）→ 中確定性（CALL_REFERENCE）→ 低確定性（USAGE）。
  3. 死碼偵測：MATCH (f:Function) WHERE NOT EXISTS { (f)<-[:CALLS]-() } AND NOT EXISTS { (f)<-[:IMPORTS]-() } RETURN f.name
  4. 近複製偵測：MATCH (a:Function)-[:SIMILAR_TO]->(b:Function) WHERE a.file_path CONTAINS '/handlers/' RETURN a.name, b.name
  5. Route 覆蓋：MATCH (r:Route) OPTIONAL MATCH (r)-[:HANDLES]->(h:Function) RETURN r.method, r.path, h.name
  6. 型別邊品質：MATCH (f:Function)-[r:CALLS]->(g:Function) WHERE f.file_path CONTAINS '/auth/' RETURN type(r), count(*) ORDER BY count(*) DESC
