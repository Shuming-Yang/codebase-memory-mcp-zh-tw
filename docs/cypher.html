Cypher 查詢

openCypher 唯讀子集——從語法到死碼偵測

這是什麼

query_graph 工具支援一個 openCypher 唯讀子集。它不支援寫入（MERGE/CALL）、不支援 list/map literals 等——超出子集的語法會回傳明確的 unsupported … 錯誤，而不是靜默回空結果。

EXISTS { … }單跳 existence——死碼偵測的關鍵

Aggregates 與 Functions

  • Aggregates：count（+DISTINCT）、sum、avg、min、max、collect
  • 圖函式：labels、type、id、keys、properties
  • 字串/轉型：toLower/toUpper/toString/toInteger/toFloat/toBoolean、trim/ltrim/rtrim、reverse、coalesce、substring、replace、left、right、size、length

實用查詢

-- 1. 死碼偵測：沒有被任何 CALLS 指向的函式
MATCH (f:Function)
WHERE NOT EXISTS { (f)<-[:CALLS]-() }
RETURN f.name
LIMIT 20
-- 2. main 呼叫鏈
MATCH (f:Function)-[:CALLS]->(g)
WHERE f.name = 'main'
RETURN g.name, count(*) AS calls
ORDER BY calls DESC
-- 3. 兩層呼叫
MATCH (f:Function)-[:CALLS*1..2]->(g)
WHERE f.name = 'main'
RETURN DISTINCT g.name
LIMIT 50
-- 4. 某套件內所有路由節點
MATCH (r:Route)-[:CONTAINS*0..]->(p:Package)
WHERE p.name = 'auth'
RETURN r.method, r.path
注意：Cypher 是唯讀。需要「整棵子圖被當值」的 path functions、parameters、comprehensions 都不支援——會明確報錯而非亂給。
看完這頁你應該能說出：Cypher 子集的邊界（讀可以、寫不行）、EXISTS 子查詢如何做死碼偵測、variable-length path 的寫法、以及不支援的語法會明確報錯。

教學解說

CBM 的 Cypher 支援是一個唯讀子集——你可以讀取圖、搜尋模式、做聚合，但不能寫入（MERGE/CREATE）。這是刻意的設計：防止意外修改圖資料。

最有價值的 Cypher 功能是 EXISTS { … } 子查詢，它讓你做「死碼偵測」（找出沒有被任何地方呼叫的函式）。Variable-length paths（[*1..3]）則讓你做多層呼叫鏈分析。

Worked Example

死碼偵測——找出專案中沒有被呼叫的函式：

-- 步驟 1：找出所有死碼候選
MATCH (f:Function)
WHERE NOT EXISTS { (f)<-[:CALLS]-() }
  AND f.name CONTAINS 'test' = false
  AND f.name STARTS WITH '_' = false
RETURN f.name, f.file_path
LIMIT 20

-- 步驟 2：進一步確認（看該函式有沒有被 IMPORTS 引用）
MATCH (f:Function)
WHERE NOT EXISTS { (f)<-[:CALLS]-() }
  AND NOT EXISTS { (f)<-[:IMPORTS]-() }
RETURN f.name, f.file_path, labels(f) AS labels

-- 步驟 3：看 main 的完整呼叫鏈（兩層深度）
MATCH path = (main:Function)-[:CALLS*1..2]->(target)
WHERE main.name = 'main'
RETURN target.name, length(path) AS depth
ORDER BY depth

進階實戰 · 找出扇入熱點與循環依賴

死碼偵測是「找沒人用」；現在反過來——找「太多人用、改了會炸」的熱點，以及「A 呼叫 B、B 又呼叫 A」的結構壞味道。

  1. 找出扇入（fan-in）最高的函式：MATCH (callee:Function)<-[:CALLS]-(caller) RETURN callee.name, callee.file_path, count(caller) AS fan_in ORDER BY fan_in DESC LIMIT 10——這些就是變更風險最高的「上帝函式」。
  2. 找出扇出（fan-out）最高的函式：MATCH (f:Function)-[:CALLS]->(g) RETURN f.name, count(g) AS fan_out ORDER BY fan_out DESC LIMIT 10——這些是「職責過載」的候選。
  3. 找 2-hop 循環：MATCH (a:Function)-[:CALLS]->(b:Function)-[:CALLS]->(a) RETURN DISTINCT a.name, b.name。
  4. 把結果送進 get_code_snippet 逐一確認，判斷是否真的需要重構。

為什麼選這條路徑：變更風險管理不能靠「感覺」。fan-in 查詢把「誰依賴這個函式」量化成可排序的數字；循環依賴查詢則抓到 grep 看不到的結構性問題。兩者都是用唯讀子集內可表達的查詢完成，不必動用到分析工具之外的任何外掛。

深入原理 · Cypher 引擎的四階段與「以為 EXISTS 是子查詢」的誤解

query_graph 不是把 Cypher 丟給資料庫，而是在 cypher.c 裡自己走完lexer → parser → planner → executor：lexer 把字串切 token（label、[*1..3]、=~ 都要辨識）；parser 用遞迴下降建 AST；planner 決定執行順序（先抓 label 數少的候選集，再做 join/filter）；executor 對 store 下 SQL、套 aggregate、處理 ORDER BY/SKIP/LIMIT/UNION。

「大家以為正確其實有誤」的案例：很多人把 EXISTS { (f)<-[:CALLS]-() } 理解成 Neo4j 的「correlated subquery（相關子查詢）」。但 CBM 的實作把它編譯成單跳存在性檢查——它驗證的是「有沒有任何一條 inbound CALLS 邊」，而不是「子查詢完整執行後回傳非空」。這在絕大多數死碼查詢上行為一致，但若你寫的是 EXISTS { (f)-[:CALLS*1..3]->(x) } 這種多跳語意，或期望子查詢內部的過濾條件被精確求值，就會得到「看似合理但其實與你想像不同」的結果。同理，WHERE 的執行順序由 planner 決定，不代表你寫的順序。

進階疑難排解

症狀可能原因解決方案
查詢要數秒才回無 label 過濾的全圖掃描，或 [*0..] 無界展開加 label 條件，把變數長度路徑改成有界（如 [*1..3]）
unsupported … 錯誤用了子集外的語法（MERGE、comprehension、parameter）查本頁支援的 Clause/Function 表，改寫成唯讀子集
回傳空，但 grep 明明找得到該呼叫該語言解析 fallback 到 USAGE/CALL_REFERENCE，沒有 CALLS 邊改用 search_graph 或把邊型換成 USAGE 再查
同一查詢兩次結果不同兩次之間 watcher 做了增量重索引（generation 變了）先確認索引狀態再下結論；查詢附上索引 generation 標註

進階挑戰題

  1. 寫一條查詢，找出「在 src/api 之下、被呼叫次數超過 5 次」的函式，並解釋為什麼要先過濾 label 再算 count。
  2. 寫一條查詢找「存在 2-hop 循環」的函式對；接著說明要偵測「N-hop 循環」時，為何 [*1..N] 會讓結果暴增。
  3. 解釋 EXISTS { … } 與「correlated subquery」在 CBM 實作上的差異，以及這個差異會在什麼樣的路徑模式上露出破綻。

專案級端到端 Worked Example — 用 Cypher 做完整的架構品質審計

假設你接手一個 Python Django 專案，要用 Cypher 做完整的架構品質審計——從死碼偵測到循環依賴到 API 覆蓋率。

  1. 索引專案：codebase-memory-mcp cli index_repository --repo-path /path/to/django-project
  2. 死碼偵測（第一輪）：MATCH (f:Function) WHERE NOT EXISTS { (f)<-[:CALLS]-() } AND f.name CONTAINS 'test' = false RETURN f.name, f.file_path LIMIT 50
  3. 死碼確認（第二輪）：MATCH (f:Function) WHERE NOT EXISTS { (f)<-[:CALLS]-() } AND NOT EXISTS { (f)<-[:IMPORTS]-() } AND NOT EXISTS { (f)<-[:USAGE]-() } RETURN f.name, f.file_path
  4. 循環依賴偵測：MATCH (a:Function)-[:CALLS*2..4]->(a) RETURN DISTINCT a.name, a.file_path LIMIT 20
  5. API 覆蓋率：MATCH (r:Route) OPTIONAL MATCH (r)-[:HANDLES]->(h:Function) WHERE h IS NULL RETURN r.method, r.path AS uncovered_routes
  6. 扇入熱點：MATCH (callee:Function)<-[:CALLS]-(caller) RETURN callee.name, count(caller) AS fan_in ORDER BY fan_in DESC LIMIT 10
  7. 結果匯出：整理成報告，標記「建議刪除」（死碼）、「建議重構」（循環依賴）。
