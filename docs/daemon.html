Session Coordination Daemon

一帳號一 daemon、共享 watcher/索引/UI、admission barrier、CLI 分離

為什麼要 daemon

你在 Claude Code、Codex、OpenCode 各開一個 session 都用 CBM——如果每個 session 各跑各的 watcher、各自索引、各自開 UI，就是浪費。CBM 用每帳號一個協調 daemon解決：

  • 第一個 daemon-backed session 啟動它，每個 session 註冊自己的 work，最後一個 session 關閉它。
  • daemon 擁有長駐背景服務：watchers、共享索引 jobs、可選的 UI。
  • 關掉一個 session 只取消「它擁有的 work」；其他 session 還需要的 work 繼續。

daemon 不依賴 MCP frontend 的 stderr

daemon 是 detached 的，它把事件寫到 owner-only 的 durable records（${CBM_CACHE_DIR}/logs）：

檔案內容
cbm-daemon.logdaemon lifecycle、watcher/indexing、UI、resource、error 事件
daemon-conflicts.ndjsonexact-build、coordination-ABI、cache-root admission 衝突
activation-events.ndjsoninstall/update/uninstall 的 activation 進度與結果

exact-build admission barrier

所有 active 的 CBM process 必須：完全相同版本 + 相同 executable build + 相同 coordination ABI + 相同 canonical cache root。等效的 CBM_CACHE_DIR alias 解析到同一個 root；真正不同的 root 在還有 CBM process active 時被拒絕。衝突會被記錄到 daemon-conflicts.ndjson。

為什麼：不同版本的二進位對同一份 SQLite 圖做讀寫，會產生 ABI/格式衝突——admission barrier 讓「混版狀態」在做事之前就失敗，而不是讓資料壞掉。

CLI 模式刻意分離

codebase-memory-mcp cli <tool> 是單次指令：不啟動也不連 daemon、不註冊 session、不啟動 watcher/UI。唯一的共享狀態是 OS admission barrier 與 per-project locks（防止同專案並行寫入衝突）。指令跑完就結束，不留常駐 process。

更新與 daemon

native install/update/uninstall 是衝突規則的刻意例外：先下載/驗證/暫存好，然後才發布維護意圖、要求 daemon 與所有暫時性操作取消、等所有 process 退出、獨佔 admission/lifetime barriers 更換二進位。成功後會提示你重啟 agent session 以載入新 build。

套件管理器（npm/PyPI/Go）只發布該套件的私有快取二進位，不會停止執行中的 session——該二進位執行時仍進同一個 admission barrier。

看完這頁你應該能說出：daemon 解決了什麼共享問題、admission barrier 為何要求 exact-build、CLI 為何刻意不連 daemon、以及更新流程「先備好再換」的安全順序。

教學解說

CBM 的 daemon 解決一個實際問題：你在多個 AI agent session 中使用同一個專案。如果每個 session 各跑各的 watcher 和索引，就是浪費資源。daemon 用「一帳號一 daemon」的模式讓多個 session 共享 watcher、索引 jobs 和 UI。

關鍵安全機制是 exact-build admission barrier：所有 CBM process 必須是完全相同版本 + 相同 build + 相同 cache root。這防止不同版本的二進位對同一份 SQLite 圖做讀寫導致資料損壞。

Worked Example

多 session 協作場景：

# Session 1（啟動 daemon）
$ codebase-memory-mcp cli index_repository --repo-path ~/my-project
# → daemon 啟動、watcher 開始、索引完成

# Session 2（連接到同一 daemon）
$ codebase-memory-mcp cli search_graph --project my-project --name-pattern '.*Handler.*'
# → 直接查詢，不需要重新索引

# Session 3（另一個 agent）
$ codebase-memory-mcp cli trace_path --project my-project --function-name Handler
# → 共享同一份圖資料

# 查看 daemon 狀態
$ cat ~/.cache/codebase-memory-mcp/logs/cbm-daemon.log | tail -20
# → 看到三個 session 的註冊記錄

進階實戰 · 從 v1 升級到 v2 的正確流程

多 session 協作是 daemon 的日常；但真正考驗 daemon 的是升級。這裡走一遍官方設計的「先備好再換」流程：

  1. 盤點現況：cat ~/.cache/codebase-memory-mcp/logs/cbm-daemon.log | tail -30——確認有幾個 active session、daemon 狀態。
  2. 觸發 update：codebase-memory-mcp update——它會先下載/驗證/暫存新二進位（此時舊版照常運作），然後才發布維護意圖。
  3. 觀察協調：維護意圖發布後，daemon 要求所有 session 取消暫時性操作、等所有 process 退出、獨佔 admission/lifetime barriers 後更換二進位。
  4. 驗證結果：cat ~/.cache/codebase-memory-mcp/logs/activation-events.ndjson——檢查 activation 進度與結果；衝突的話看 daemon-conflicts.ndjson。
  5. 重啟 session：提示「重啟 agent session 以載入新 build」後，關閉再重開。

為什麼選這條路徑：很多人會直接刪掉二進位再裝新的——這在 active 的 daemon 還在跑時是災難（混版讀寫同一份 SQLite）。官方的順序把「下載」與「替換」拆開，中間用 admission barrier 擋住混版狀態，這是「讓衝突在做事之前就失敗」的設計。

深入原理 · daemon 的內部協調與「以為 CLI 完全離線」的誤解

daemon 不是一個抽象概念，而是一組明確的元件：bootstrap.c 處理 daemon 啟動與鎖、ipc.c 封裝前台 session ↔ daemon 的通訊（endpoint、frame 收送、lifetime reservation、startup gate，POSIX vs Windows 差異被抽象掉）、application.c 排程「索引 job」（有物理上限、busy queue、可被 activation 取消）、runtime.c 管 worker/process 生命週期、project_lock.c 提供 per-project 的 OS-backed 鎖。

「大家以為正確其實有誤」的案例：文件說「CLI 模式刻意分離——不啟動 daemon、不留常駐 process」，於是很多人以為「跑 codebase-memory-mcp cli index_repository 是完全孤立的、不會影響其他 session」。但 CLI 模式仍然參與 OS admission barrier，並會拿 per-project lock——它只是不註冊 session、不開 watcher。也就是說，一個 CLI 索引在跑的同時，MCP session 對同一專案的寫入會被 per-project lock 序列化。把「不連 daemon」解讀成「與其他 session 零互動」是錯的。

進階疑難排解

症狀可能原因解決方案
daemon-conflicts.ndjson 出現記錄exact-build admission 失敗：版本/build/cache root 不一致關閉所有 session 統一版本；檢查 CBM_CACHE_DIR 是否被多帳號混用
