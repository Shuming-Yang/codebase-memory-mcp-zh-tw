安全模型

SLSA3 / cosign / VirusTotal / CodeQL、零依賴、無 telemetry

這個工具做什麼（先講清楚）

CBM 讀取你的 codebase，並寫入你的 agent 設定檔——這是它的設計本質。安裝前先知道這件事；想先稽核再看原始碼。

Supply chain 安全

防護層說明
VirusTotal每個 release 二進位被 70+ 防毒引擎掃描（零偵測才發布）
SLSA Level 3受信任的 GitHub Actions 建置流程產生的加密建置來源證明；用 gh attestation verify 驗證
Sigstore cosign所有 artifact 的 keyless 簽章
SHA-256 checksums每個 release 附 checksums.txt，安裝指令碼在解壓前驗證
CodeQL SAST有未關閉的 alert 就擋 release pipeline
零 runtime 依賴無供應鏈傳遞風險——所有函式庫在編譯時 vendored

隱私

  • 100% 本機處理：所有解析、索引、語意搜尋都在本機跑，你的程式碼不會離開機器。
  • 無 telemetry、無 phoning home：CBM 不會自行發任何網路請求，不會背景檢查新版本。
  • 內建 embedding 模型：nomic-embed-code（768d int8）編譯進二進位——語意搜尋不需要 API key、Ollama、Docker。

安裝的安全性設計

  • 不搞 in-process updater：更新交給外部 install.sh（避免二進位裡內建「下載 + 解壓 + 執行」的 dropper 特徵）。
  • 不亂開設定：installer 絕不翻開實驗性 feature flag、不啟用 plugin、不做 global permission bypass、不信任第三方指令。
  • Conditional 安裝：只有當平台的 marker / 已存在的 config 路徑證明它 active 才寫入設定。
  • exact-build admission barrier：所有 CBM process 必須同版本、同建置、同 cache root，防止混版狀態。

診斷 log（疑難排解用）

因為無 telemetry，出了無法重現的問題時要自己抓資料。設 CBM_DIAGNOSTICS=1 後重開 daemon session：

檔案內容
trajectory.ndjson每 5 秒一行記憶體軌跡（rss/committed/peak/page_faults/fd/queries）——記憶體/洩漏回報要的就是它
snapshot.json最新快照（乾淨退出時移除）

路徑在 ${CBM_CACHE_DIR}/logs/cbm-daemon.log 的 diagnostics.start 事件裡；使用隨機目錄避免其他帳號預置惡意連結。

重要環境變數

變數用途
CBM_ALLOWED_ROOT把 index_repository 限制在此目錄內（未被信任的呼叫者/多租戶部署時用）
CBM_CACHE_DIR覆寫 DB 存放目錄（一帳號只能用一個 canonical cache root）
CBM_LOG_LEVELlog 級別：debug/info/warn/error/none
看完這頁你應該能說出：CBM 的 supply chain 六層防護、為何沒有 telemetry 又該怎麼自己抓診斷資料、installer 的三個「絕不」、以及 CBM_ALLOWED_ROOT 何時該設。

教學解說

CBM 的安全模型有六層防護：VirusTotal（70+ 防毒引擎掃描）、SLSA Level 3（建置來源證明）、cosign（keyless 簽章）、SHA-256 checksums、CodeQL SAST、零 runtime 依賴。

隱私方面：CBM 100% 本機處理、無 telemetry、無 phoning home。語意搜尋的 embedding 模型（nomic-embed-code）編譯進二進位，不需要外部 API。

Worked Example

驗證 CBM 二進位的安全性：

# 1. 下載 CBM 後驗證 checksum
curl -LO https://github.com/DeusData/codebase-memory-mcp/releases/latest/download/checksums.txt
sha256sum -c checksums.txt --ignore-missing

# 2. 驗證 cosign 簽章
gh attestation verify codebase-memory-mcp --owner DeusData

# 3. 驗證 SLSA provenance
gh attestation verify codebase-memory-mcp --owner DeusData --predicate-type https://slsa.dev/provenance/v1

# 4. 啟用診斷（需要回報問題時）
CBM_DIAGNOSTICS=1 codebase-memory-mcp cli index_repository --repo-path ~/project
# → 產生 trajectory.ndjson 和 snapshot.json

常見錯誤 / 診斷

症狀原因解法
checksum 驗證失敗下載不完整或被竄改重新下載並再次驗證
cosign 驗證失敗gh CLI 未登入或版本過舊gh auth login 後重試
診斷 log 未產生CBM_DIAGNOSTICS 未在 daemon 啟動前設定關閉所有 session，設定環境變數後重開

進階實戰 · 在共用 CI runner / 多租戶環境的安全硬化

個人筆電上的安全，和「共用 CI runner 或多人共用的機器」上的安全，是兩個等級。後者的實戰流程：

  1. 限制可索引範圍：設 CBM_ALLOWED_ROOT=/workspace/projects——把 index_repository 限制在此目錄內，防止未被信任的呼叫者把任意路徑塞進來。多租戶部署尤其需要。
  2. 驗證 artifact / 二進位來源：sha256sum -c checksums.txt + gh attestation verify（SLSA3 provenance）+ cosign 驗證——三層獨立來源信任，缺一不可。
  3. 最小化設定面：installer 原則上「絕不翻開實驗性 flag、不啟用 plugin、不做 global permission bypass、不信任第三方指令」——部署時也一樣，別手動加寬。
  4. 出問題時自己抓診斷：共用環境出了無法重現的問題，設 CBM_DIAGNOSTICS=1 後重開 daemon session，蒐集 trajectory.ndjson（每 5 秒一行記憶體/查詢軌跡）回報。診斷目錄用隨機名稱，避免其他帳號預置惡意連結。
  5. 審計清單：把「零 runtime 依賴、無 telemetry、embedding 模型編進二進位」寫進團隊的安全準則，讓所有人知道沒有隱藏外傳。

為什麼選這條路徑：共用環境最怕兩件事——（1）工具能碰它不該碰的目錄，（2）團隊無法驗證自己跑的是不是真的官方二進位。前者靠 CBM_ALLOWED_ROOT，後者靠 checksum + provenance + cosign 三層驗證。診斷流程則彌補「無 telemetry」的短板：不偷傳資料，但出事時給你抓資料的方法。

深入原理 · Supply chain 管線與「以為驗證 checksum 就夠了」的誤解

CBM 的供應鏈防護是六層：VirusTotal（70+ 引擎零偵測才發布）→ SLSA Level 3（GitHub Actions 產生的加密建置來源證明）→ cosign keyless 簽章 → SHA-256 checksums → CodeQL SAST 擋 release → 零 runtime 依賴（所有函式庫編譯時 vendored）。embedding 模型（nomic-embed-code，768d int8）也編譯進二進位，所以語意搜尋不需要 API key / Ollama / Docker，也不會為此外傳任何東西。

「大家以為正確其實有誤」的案例：很多人驗完 sha256sum -c 就覺得「來源可信」。但 checksum 只證明「你拿到的和發布者算的一致」——如果發布者被入侵、或有人偽造了 checksums.txt 與二進位的組合，checksum 驗證照樣過。要證明「這真的是 DeusData 官方建置」，必須驗 SLSA provenance 與 cosign 簽章（gh attestation verify）——那是綁定到 GitHub 身分的加密證據。三層都要驗，不是驗一層。

進階疑難排解

症狀可能原因解決方案
checksum 驗證失敗下載不完整或被竄改重新下載並重驗；仍失敗就從官方 release 頁換鏡像
gh attestation verify 失敗gh CLI 未登入、版本過舊、或 network 到 GitHub 受限gh auth login、升級 gh、或改用 cosign CLI 驗證
診斷 log 沒產生CBM_DIAGNOSTICS 在 daemon 啟動前未設定關閉所有 session，設定環境變數後重新啟動再觸發
索引 CBM_ALLOWED_ROOT 之外的目錄被拒這是預期行為（限制生效）調整 CBM_ALLOWED_ROOT 範圍，或改用被允許的目錄
「無 telemetry」卻看到對外連線可能是其他工具的請求，或被誤判用 lsof/網路監控確認來源 process；CBM 本身不發網路請求

進階挑戰題

  1. 設計一份「CBM 供應鏈審計 checklist」，涵蓋下載、驗證、安裝、執行四個階段，每階段至少三項檢查。
  2. 解釋「checksum 驗證通過」與「來源可信」之間還缺哪一環，以及 SLSA/cosign 如何補上。

專案級端到端 Worked Example — 在共用 CI Runner 上安全部署 CBM

假設你的團隊在 GitHub Actions self-hosted runner 上使用 CBM，要確保供應鏈安全、多租戶隔離、以及問題時能抓到診斷。

  1. 下載與驗證：sha256sum -c checksums.txt --ignore-missing——第一層 checksum。
  2. 驗證簽章：gh attestation verify codebase-memory-mcp --owner DeusData——第二層 SLSA3。
  3. 驗證 cosign：cosign verify-blob codebase-memory-mcp ...——第三層 keyless 簽章。
  4. 限制範圍：CBM_ALLOWED_ROOT=/workspace/projects。
  5. 最小化設定：installer 絕不翻開實驗性 flag、不啟用 plugin。
  6. 啟用診斷：CBM_DIAGNOSTICS=1——蒐集 trajectory.ndjson。
  7. 審計清單：把「零 runtime 依賴、無 telemetry」寫進團隊安全準則。
