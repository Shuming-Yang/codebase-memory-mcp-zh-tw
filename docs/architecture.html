索引 pass 順序

索引不是一個大函式，而是一串 pass，各自職責單一：

Pass做什麼
pass_definitions抽取函式/類別/方法等定義節點
pass_calls建 CALLS 邊（import-aware、型別推斷）
pass_lsp_cross / lsp_surfaceHybrid LSP 跨檔型別解析
pass_route_nodesREST 端點變一級圖實體（Route 節點）
pass_cross_repo跨 repo 的 CROSS_* 邊
pass_infrascan / pass_k8sIaC：Dockerfile、K8s manifests、Kustomize overlays
pass_pkgmap套件解析（package.json / go.mod / Cargo.toml / pyproject.toml…）
pass_similarityMinHash + LSH 近複製偵測（SIMILAR_TO）
pass_semantic*語意邊（SEMANTICALLY_RELATED）
pass_gitdiff / pass_githistory變更耦合（detect_changes 用）
pass_parallel平行 worker 調度（worker pool）

看完這頁你應該能說出：CBM 由哪幾個模組組成、索引是「多 pass」而非單一函式、Hybrid LSP 夾在 tree-sitter 與 store 之間做型別精煉、以及哪些 pass 產出 Route / CROSS_* / SIMILAR_TO 邊。

教學解說

CBM 的架構可以一句話總結：「發現 → 解析 → 存儲 → 查詢」。discover 模組負責找出哪些檔案要索引；pipeline 的多 pass 管線（tree-sitter AST → Hybrid LSP 型別精煉 → HTTP route → IaC → 相似度）把原始碼變成結構化的節點與邊；store 模組用 SQLite 存圖；最後 15 個 MCP 工具暴露查詢能力。

理解架構的關鍵是：索引不是一個大函式，而是一串 pass 各司其職。這讓 CBM 可以只跑需要的 pass（增量更新）、平行化（pass_parallel.c）、以及在不同語言間共享相同的 store/cypher 基礎設施。

Worked Example

假設你有一個 Node.js 專案，想了解「哪些模組呼叫了 processOrder 函式」：

  1. 先索引專案：codebase-memory-mcp cli index_repository --repo-path /path/to/project
  2. 用 search_graph 找到確切名稱：codebase-memory-mcp cli search_graph --project my-project --name-pattern '.*processOrder.*' --label Function
  3. 用 trace_path 追蹤呼叫鏈：codebase-memory-mcp cli trace_path --project my-project --function-name processOrder --direction inbound
  4. 或用 Cypher 做更精確的查詢：codebase-memory-mcp cli query_graph --project my-project --query "MATCH (f:Function)-[:CALLS*1..3]->(g) WHERE g.name = 'processOrder' RETURN f.name, length(shortestPath((f)-[:CALLS*]->(g))) AS depth"

這四步從「索引 → 發現 → 追蹤 → 深度查詢」，展示了架構中各模組的協作。

進階實戰 · 大型 monorepo 的跨服務耦合審計

前面的例子是「單一函式的呼叫鏈」。現在換一個真正的大場面：一個 12 個微服務、5 種語言（Go/Python/TS/Java/Kotlin）、20 萬檔的 monorepo，你要回答「改 auth 服務會炸到哪些服務」。

  1. 先索引整個 monorepo：codebase-memory-mcp cli index_repository --repo-path /path/to/monorepo（RAM-first 管線在這種規模下建議先設 CBM_WORKERS）。
  2. 看全域架構：get_architecture(project="monorepo", aspects=["clusters","boundaries"])——Louvain 社群會把「一起工作的函式」聚成群，先建立鳥瞰。
  3. 找出跨服務的 HTTP 呼叫：query_graph --query "MATCH (a:Function)-[:HTTP_CALLS]->(b:Function) WHERE a.file_path CONTAINS '/auth/' RETURN b.file_path, count(*) AS hits ORDER BY hits DESC"——用真實的 HTTP_CALLS 邊而非猜測。
  4. 對未 commit 的變更做爆炸半徑分析：detect_changes(project="monorepo")——它會把 git diff 映射到受影響符號並標上風險等級。
  5. 用 get_code_snippet 深入關鍵節點，確認改動點。

為什麼選這條路徑：這類「跨服務影響」問題靠 grep 要搜遍 20 萬檔；靠人腦逐 service 追更不可能。CBM 的價值在於 HTTP_CALLS/CROSS_* 邊讓跨服務耦合可被查詢，而 detect_changes 把「改哪一行」直接映射成「影響哪些符號」——這是單靠文本搜尋做不到的。

深入原理 · 多 pass 管線的執行模型與「看似正確卻有誤」的索引

架構上最容易誤解的一點：索引不是「跑一次」，而是每一輪都有順序依賴的 pass 串。pipeline 依 registry.c 註冊的順序依序執行：pass_definitions（建節點）→ pass_calls（建 CALLS）→ pass_lsp_cross（型別精煉）→ …→ pass_route_nodes / pass_cross_repo / pass_similarity。前面的 pass 若不產出某種節點，後面的 pass 就沒有輸入——所以「看起來都叫 pass」不代表彼此獨立。

平行的部分是 pass_parallel.c 的 worker pool，它平行的是逐檔抽取；合併與跨檔解析（Hybrid LSP、Louvain）仍然是聚合階段。這就是為什麼 worker 數不是越高越好（見下方排解表）。

「大家以為索引正確但其實有誤」的案例：你 trace 一個函式，發現它沒有 inbound CALLS 邊，於是斷言「這是死碼」——但真相可能是：這個函式是經由 symlink 路徑或 .gitignore 排除的檔案定義的，根本沒進圖；或是語言不在 Hybrid LSP 支援清單，解析 fallback 成 USAGE（不保證唯一的引用），所以沒有 CALLS 邊。索引的「正確」是相對於當時的 discover 規則與語言支援範圍的，不是絕對正確。驗證手段：先跑 get_graph_schema 看該函式的實際邊型，再用 check_index_coverage 確認檔案真的被索引。

進階疑難排解

症狀可能原因解決方案
get_architecture 的 routes 是空的pass_route_nodes 未執行，或框架不在支援清單確認索引時沒有 skip route pass；查 upstream 支援的 framework 清單
跨 repo 查不到 CROSS_* 邊兩個 repo 沒有 index 進同一個 store，或未用 cross-repo-intelligence 模式確認兩者 project 在同一 cache root，必要時用 cross-repo 模式重 index
設 CBM_WORKERS=64 反而更慢worker 過多造成記憶體壓力與合併階段鎖競爭逐步調降（建議 CPU 核心數 1–2 倍），觀察索引時間曲線
cluster 與資料夾結構對不上Louvain 只看 CALLS 邊密度，跨目錄的高耦合函式會聚在一起這不是 bug——把 cluster 當「實際功能模組」而非目錄鏡像
改了 code 但查詢結果沒變watcher 未啟用（auto_watch false）或增量尚未觸發config set auto_watch true，或手動重跑 index_repository

進階挑戰題

  1. 寫一條 Cypher，找出「兩個服務之間存在循環 HTTP 依賴」的配對（提示：HTTP_CALLS 邊 + path 比較）。
  2. 你發現某函式沒有 inbound CALLS 卻仍被執行——列出至少三種「索引看似正確其實有誤」的可能，並寫出對應的驗證工具呼叫。
  3. 解釋為何「平行化抽取」與「聚合型 pass」不能簡單地全部打散到 worker 上。
