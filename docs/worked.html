教學解說

實作案例展示 CBM 的真實產出——不是示意圖，而是用 graphify 工具掃描 CBM 自己的源碼產生的互動知識圖譜。這是一個「meta 示範」：用一個知識圖譜工具分析另一個知識圖譜工具。

343 個社群自然地對應 CBM 的模組結構（Cypher engine、MCP server、Daemon IPC…），側面驗證了 CBM 的架構乾淨度。

Worked Example

重現 CBM 源碼知識圖譜的步驟：

# 1. 安裝 graphify
uv tool install graphifyy

# 2. 準備語料
git clone https://github.com/DeusData/codebase-memory-mcp.git cbm
mkdir corpus && cp -R cbm/src corpus/ && cp -R cbm/tests corpus/

# 3. 跑 code-only 分析
graphify corpus --code-only

# 4. 產出在 graphify-out/
ls graphify-out/
# → graph.html（互動圖）、graph.json（全量資料）、GRAPH_REPORT.md（審計報告）

# 5. 中文化（選擇性）
cp graphify-out/graph.html graphify-out/graph-zh.html
# 替換 UI 字串

常見錯誤 / 診斷

症狀原因解法
graphify 安裝失敗套件名是 graphifyy（雙 y）用 uv tool install graphifyy
互動圖只顯示社群聚合節點數超過 5,000 上限縮小語料範圍或用社群檢視
審計報告缺少某些模組語料排除了 vendored grammars這是預期行為（只分析第一方程式碼）

進階實戰 · 用 CBM 分析 CBM 自己（meta 實作）

前一個案例用 graphify 掃描 CBM 源碼；現在用 CBM 掃描 CBM 自己——兩個知識圖譜工具互相分析，你會看到它們「看到不同的東西」：

  1. 索引：codebase-memory-mcp cli index_repository --repo-path /path/to/cbm（對齊 commit 2c50c77 的 src/ + tests/）。
  2. 看 CBM 眼中的架構：get_architecture(project="cbm", aspects=["clusters","entry_points","hotspots"])——Louvain 社群會把 CBM 的模組聚出來。
  3. 找核心抽象（god node）：query_graph --query "MATCH (f:Function) RETURN f.name, f.file_path, count{ (f)-[:CALLS]->() } AS out, count{ (f)<-[:CALLS]-() } AS in ORDER BY (out+in) DESC LIMIT 10"——找出被最多人呼叫、呼叫最多人的「樞紐函式」。
  4. 找測試熱點：query_graph --query "MATCH (m:Method)-[:CALLS]->(t) WHERE t.file_path CONTAINS '/tests/' RETURN m.file_path, count(*) ORDER BY count(*) DESC"——看測試群集中壓測哪個模組。
  5. 交叉對照：把 CBM 的 clusters 與 graphify 的 343 個社群比較——兩者都會「分群」，但分法不同（邊密度 vs AST 結構）。

為什麼選這條路徑：這是對「meta 示範」的升級。graphify 展示「視覺化」，CBM 展示「可查詢的結構化分析」。用同一個 codebase 跑兩套，能最直觀地比較兩個工具的哲學差異——也順便驗證 CBM 對「C 語言（Hybrid LSP 有支援）」的解析品質。

深入原理 · graphify vs CBM 的分群哲學與「以為社群=模組邊界」的誤解

graphify 用 code-only AST 抽取 + 圖社群偵測，產出「視覺化的互動知識圖譜」；CBM 用 tree-sitter + Hybrid LSP 產出「型別感知的呼叫圖」，並用 Louvain（只看 CALLS 邊密度）把「一起工作的函式」聚成 cluster，再由 get_architecture 彙整成報告。兩者都有「社群/cluster」，但輸入完全不同：graphify 看 AST 結構，CBM 看型別解析後的呼叫關係。

「大家以為正確其實有誤」的案例：看到 343 個社群或 cluster 名稱，很多人直接把它當成「模組邊界」——「既然 CBM 說這 20 個函式是一群，它們應該在同一個目錄、同一個套件」。但 Louvain 只依邊密度分群：如果 utils/ 裡某個函式被 5 個不同模組重度呼叫，它會跟「呼叫它的那群」聚在一起，而不是跟 utils/ 的鄰居。所以 cluster 反映的是實際的耦合結構，不是宣告的目錄結構——把兩者混為一談，是解讀架構報告最常見的錯誤。

進階疑難排解

症狀可能原因解決方案
CBM 索引 C 專案時 CALLS 邊比預期少C 的 macros/typedef 鏈讓部分解析 fallback 到 USAGE接受 C 語言的解析極限；關鍵路徑用 search_code 補查
graphify 與 CBM 的社群對不上兩者演算法與輸入語料不同，並非一致把它當「互補視角」，不要期待一比一
圖太大瀏覽器卡死節點數超過前端渲染上限用社群聚合檢視；或縮小語料範圍
god node 查詢回傳空count{ } 語法不在子集內（部分版本不支援 pattern comprehension）改用有向邊的 MATCH + count() 聚合
測試熱點查不到tests/ 被 .gitignore 排除或未索引確認 tests/ 有進圖；用 check_index_coverage 驗證

進階挑戰題

  1. 比較 graphify 與 CBM：同樣掃 CBM 源碼，兩者各自「看得到」與「看不到」什麼？（至少各列三項）
  2. 用 get_architecture 的 cluster 找出 CBM 的「核心抽象」（被跨模組重度依賴的樞紐），並驗證它是否就是 store/ 或 cypher/。
  3. 解釋「Louvain cluster 是實際耦合結構、不是目錄結構」——舉一個具體的場景說明這如何改變你對架構報告的解讀。
