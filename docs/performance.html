效能基準

Linux kernel 3 分鐘、Cypher <1ms、token 省 99.2%
出處聲明：以下數字為上游官方 benchmark（Apple M3 Pro、docs/BENCHMARK.md），本站未在同等硬體重測——列出來是讓你知道這工具「能多快」，不是本站實測。

為什麼快

  • RAM-first pipeline：所有索引在記憶體跑（LZ4 HC 壓縮讀入、in-memory SQLite、結束才單次 dump）。
  • 平行 worker：pass_parallel.c 的 worker pool 用滿 CPU。
  • 記憶體用完即釋放：索引完回歸 OS，不常駐。
  • 增量更新：之後只處理變更，不是每次全跑。

Token 效率

官方 benchmark：5 個結構查詢約 3,400 token，而逐檔 grep 探索同一批問題約需 412,000 token——減少 99.2%。

file-by-file grep:  ~412,000 tokens

省下:                99.2%

圖查詢取代幾十次 grep/read 循環：agent 不用把整個檔案塞進 context 才能找到答案。

教學解說

CBM 的效能有三個關鍵數字：3 分鐘（Linux kernel 全索引）、<1ms（Cypher 查詢）、99.2%（token 節省）。這些數字的背後是 RAM-first pipeline + 平行 worker + 增量更新的工程結果。

Token 節省 99.2% 的意義是：用 CBM 做 5 次結構查詢大約花 3,400 token，而用 grep 逐檔探索同樣的問題大約要 412,000 token。這直接影響你的 AI agent 的成本與回應品質。

Worked Example

比較 CBM 與 grep 的 token 消耗：

# 方法 1：grep 逐檔探索（低效）
grep -r "ProcessOrder" --include="*.ts" src/ | head -20
# → 回傳 50 行原始碼，agent 需要全部讀完才能判斷
# → 約消耗 80,000 token（如果檔案很大）

# 方法 2：CBM 圖查詢（高效）
trace_path(project="my-project", function_name="ProcessOrder", direction="inbound")
# → 直接回傳結構化結果：[{caller: "OrderService.create", depth: 1}]
# → 約消耗 680 token

# 方法 3：Cypher 精確查詢
query_graph(project="my-project", query="MATCH (f:Function)-[:CALLS]->(g:Function) WHERE g.name = 'ProcessOrder' RETURN f.name")
# → 約消耗 500 token

三次查詢總計 <2,000 token，而 grep 方式可能要 200,000+ token。

進階實戰 · 把 10M LOC 的 monorepo 索引時間壓進 5 分鐘

官方的 3 分鐘 kernel 是參考值；你的 monorepo 可能更大或硬體更弱。這裡是一套可重複的調校流程：

  1. 先測基準線：time codebase-memory-mcp cli index_repository --repo-path /path/to/monorepo——先知道「無腦跑」要多久。
  2. 檢查 worker 數：先確認機器的 CPU 核心數；若在容器/CI 裡，cgroup 配額可能誤判 worker 數。CBM_WORKERS 手動覆寫成「核心數 × 1.5」做第一次實驗。
  3. 決定模式：上線初期用 fast 模式拿到可用圖：--mode fast（跳過 similarity/semantic 這類重 pass，換速度）；之後讓 watcher 用增量慢慢補 full 等級的邊。
  4. 設記憶體上限：大型 repo 需要 CBM_MEM_BUDGET_MB，避免吃到 swap：先設機體 RAM 的 60%，逐步調。
  5. 驗證：索引完用 index_status 看節點/邊數與 generation，確認沒有悄悄 skip 掉關鍵 pass。

為什麼選這條路徑：效能不是「一個參數」，而是「worker × 模式 × 記憶體 × 增量」的組合。先量測再調參，比盲目設 CBM_WORKERS=64 可靠。

深入原理 · RAM-first 管線的記憶體生命週期與「以為 worker 越多越快」的誤解

RAM-first 的意思是：索引全程在記憶體跑，結束才單次 dump 到磁碟。具體是：LZ4 HC 壓縮讀入原始檔 → in-memory SQLite（節點/邊先放記憶體）→ 多 pass 管線 → 單次落盤 → 記憶體回歸 OS。平行化由 pass_parallel.c 的 worker pool 提供，pass_parallel 平行的是「逐檔抽取」，聚合與跨檔解析仍是串行的收尾階段。增量更新則靠 watcher 偵測 git 狀態、用 adaptive interval 平衡即時性與資源。

「大家以為正確其實有誤」的案例：直覺上「設 CBM_WORKERS=64 一定比 8 快」。但實際上是：worker 數超過 CPU 實體核心後收益遞減，甚至變慢——因為記憶體被同時展開的檔案壓縮流吃光，進入 swap；且聚合/合併階段要等所有 worker，worker 太多反而放大同步開銷。正確做法是逐步升到平台值後測量曲線，找「轉折點」而不是「最大數」。

進階挑戰題

  1. 假設一台 8 核心、32GB RAM 的機器要索引 10M LOC：你依序調整哪三個參數、期望觀察到什麼訊號？（附上你的判斷規則）
  2. 估算一次「5 個結構查詢 vs 逐檔 grep」的 token 消耗比，並列出假設條件——說明為何 99.2% 不是適用在所有場景。
  3. 設計一個微型 benchmark：用同一份 repo 比較「fast 模式」與「full 模式」的索引時間、節點數、查詢延遲，並寫出你會怎麼解讀差異。
